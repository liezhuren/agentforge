# AgentForge

多智能体协作软件开发系统。五个 LLM 角色（PM / 前端 / 后端 / 测试 / 主理人）加一个**非 LLM 的机械裁判**，
围绕**接口**而不是"对话"协作，用**多层确定性锚点**压制幻觉，用**问责账本 + 推进保证**驯服对抗性审查者。

> 状态：**P0–P4、P6 已完成，P3 靶场标定已完成，真人建议书已真正生效，P5 圆桌机制完成**。
> **192 个测试全绿**。剩余：用真实 LLM 重跑 P6 与真实多角色辩论，并据此标定经验参数（见 `docs/06-roadmap.md`）。

---

## 0. 先跑起来看

**引擎零依赖**：`packages/*` 只需要 Node ≥ 24（自带 TypeScript 类型剥离），不需要 `npm install`。
**控制台**需要 React/Vite，独立安装。

```bash
# ── 引擎（无需安装任何东西）─────────────────────────────
node scripts/run-tests.ts                      # 全部测试（192 个）
node scripts/run-tests.ts roundtable           # 只跑匹配的测试文件（调试用）
node scripts/anchor-benchmark.ts               # 幻觉靶场（42 样本，出 docs/10）
node packages/orchestrator/src/cli-e2e.ts      # 端到端闭环演示（离线）
node packages/orchestrator/src/cli.ts          # 垂直切片演示（锚点 / 裁判 / 账本）

# ── P6 自举验证：生成一个真实小应用并独立验证 ──────────
node scripts/verify-real-app.ts                # 首次需要 npm 下载 typescript（之后有缓存）

# ── 接真实 LLM ────────────────────────────────────────
node packages/orchestrator/src/cli-run.ts init                    # 生成 agentforge.config.json
node packages/orchestrator/src/cli-run.ts --brief "做一个任务看板"  # 真实 run
node packages/orchestrator/src/cli-run.ts --replay <runId>        # 离线回放（零成本）

# ── 控制台 ────────────────────────────────────────────
cd apps/web && npm install && npm run build && cd ../..
node packages/server/src/cli.ts                # 打开 http://127.0.0.1:7788
```

### P3 · 锚点到底抓得住幻觉吗

用户的核心诉求是「多层检测锚点防止幻觉」。在 P3 之前我们只能说「A2 能抓出幻觉符号」（因为有测试），
**说不出它的检出率与误报率** —— 而这两个数字才决定机制的价值。

`node scripts/anchor-benchmark.ts` 用 **42 个样本（28 注入 + 14 干净对照）** 把它变成数据：

| 指标 | 值 |
|---|---|
| 检出率（注入样本被抓到的比例） | **100%** |
| **干净通过率（对照组零误报）** | **100%** |
| 漏报 / 误报 | 0 / 0 |

**为什么必须有干净对照组**：只测「能不能抓出问题」毫无意义 ——
一个永远返回 FAIL 的锚点检出率是 100%。误报与漏报**同样有害**：
漏报让幻觉通过；误报把诚实代码判成幻觉，角色被派去修一个不存在的问题。

**靶场抓到的两个真实缺陷**（已修）：

1. **A5**：测试命令退出 0 但输出里没有任何可解析的计数 → 原本报 `PASS`。
   它其实什么都没验证到 —— 违反 `SKIPPED ≠ PASS`。
2. **A7**：端点只写在注释里（`// TODO: 实现 /api/tasks`）→ 端点覆盖检查是子串匹配，被注释骗过。

> 首轮跑出「0 误报 0 漏报」时没有被当成好消息：
> **一次就全过通常意味着样本太贴合被测对象的强项**。主动加对抗性样本之后才抓到这两个洞。

**这份报告的局限也写在报告里**：样本是手写的（自出题自答）；
**A1 的远端核实未纳入 —— 这是当前最大的一块未覆盖区域**（编造一个名字合法、
也不像知名包的假包，本靶场抓不到）；没有测量「语义用错」这类隐蔽幻觉（那属于 B 层，依赖 LLM）。
详见 `docs/10-anchor-benchmark.md`。

### P6 · 它真的能生成一个能跑的软件吗

`node scripts/verify-real-app.ts` 做两件事，第二件事**不依赖第一件的任何结论**：

1. **流水线**：走完 `INTAKE → DELIVERED`，A1–A7 七个锚点**全部真实执行**（无 SKIPPED）
2. **独立验证**：绕开锚点系统，直接对产物做真编译 / 真测试 / 真启动 + 真 HTTP 请求

一次真实结果（报告见 `docs/09-field-report.md`，由脚本自动生成）：

```
A4 PASS  638ms  structured diagnostics from npm run typecheck     ← 真的跑了 tsc
A5 PASS  444ms  structured counts from npm run test               ← 真的跑了测试
A6 PASS  347ms  spawn + HTTP probe http://127.0.0.1:39517/health  ← 真的起了服务

独立 tsc --noEmit（直接对生成产物运行）      — 零类型错误
独立运行应用自己的测试套件                   — exit=0 pass=3 fail=0
POST /api/tasks → 201 且返回带 id 的 Task    — {"id":"T-001","title":"写文档"}
GET  /api/tasks → 200 且包含刚创建的任务      — {"items":[{"id":"T-001","title":"写文档"}]}
```

**为什么必须分成两段**：如果只用「锚点全绿」来证明「应用能用」，那就是自证 ——
锚点自己有 bug 时两者会一起错。第二段是外部证据。

**诚实边界**：当前环境没有可用的 LLM API key，因此**「模型写了什么」是脚本化的**
（MockProvider 精确返回这份应用代码）。流水线、锚点、裁判、账本、逃生、独立验证全部是真的。
**这证明了**：给定一份确定的应用代码，整套机制的检查、归因、裁决与交付流程正确工作。
**它没有证明**：任意 LLM 在任意需求下都能产出这样的代码 —— 那需要真实模型，属于未完成的验证。

### 用你自己的 LLM

控制台打开后**先点「离线演示」** —— 四个预设场景（干净项目 / 幻觉+说谎 / 甩锅+和稀泥 / 交叉质询）
都不需要任何 API key，几秒钟就能把整套机制跑一遍看懂：

- **流水线 + 锚点红绿灯**：每个锚点悬停可看方法、权威度与每条发现（含文件行号与机械归因）
- **主理人账本**：precision 条、有效/误报/不可证伪、额度、阻断尝试、观察期 —— 每个数字都有 tooltip 说明它对应哪条规则
- **真人介入区（首屏可达）**：五种建议书 + 立即暂停 + 待裁决收件箱
- **审查视图**：每条异议的裁决理由都带**规则编号**（R2/R6/R9/R-contradicts-anchor…），人类据此复查裁判是否误判
- **工件浏览器**与**事件流**（前端只是投影，刷新/重连不丢状态）

### 用你自己的 LLM

`agentforge.config.json` 里**每个角色**可以独立绑定 provider 与模型：

```jsonc
"roles": {
  "pm":       { "provider": "deepseek", "model": "deepseek-chat",     "temperature": 0.3 },
  "host":     { "provider": "deepseek", "model": "deepseek-reasoner", "temperature": 0.1 },
  "frontend": { "provider": "ollama",   "model": "qwen2.5:14b" },
  "backend":  { "provider": "ollama",   "model": "qwen2.5:14b" },
  "test":     { "provider": "deepseek", "model": "deepseek-chat",     "maxTokens": 8192 }
}
```

组合是有讲究的：**契约质量与找茬质量决定后续一切**，所以 PM 与主理人值得用最强的模型；
前后端代码量大、A 层锚点会兜底，可以用便宜甚至本地的模型。
支持 `${ENV_VAR}` 引用环境变量，不必把 key 写进文件。详见 `docs/08-llm-layer.md`。

首次使用某个模型时会**自动探测**它的结构化输出能力（strict → json-mode → prompt-only 三级降级），
并把证据缓存下来 —— 因为「模型能不能可靠地吐 JSON」这件事**不能猜**。

### 端到端演示的四个场景

`cli-e2e.ts` 全部离线运行，用 MockProvider 精确注入幻觉，验证确定性编排内核：

**场景 A · 干净项目** —— 一次通过到 `DELIVERED`，主理人 precision 100%，零技术债。

**场景 B · 幻觉 + 主理人说谎**：

```
INTAKE       ADVANCE→PLANNING      [未唤醒主理人]
PLANNING     ADVANCE→CONTRACTING   [未唤醒主理人]
CONTRACTING  ADVANCE→BUILDING      [未唤醒主理人]
BUILDING     ADVANCE→REVIEW        [未唤醒主理人]
    阻断：ANCHOR_HARD_FAIL
REVIEW       ADVANCE→DELIVERED     [唤醒主理人]

派工单：WO-001 → backend (锚点失败)
  验收：修正 src/api/routes.ts:1 中对 "leftpad-real" 的符号导入
        （符号 padRigth 不存在），使 A2 锚点 PASS

账本：precision 0%   有效异议 0   误报 1
```

三个关键点：
- A2 锚点抓出幻觉符号并**机械归因**给 backend —— 编译器/类型检查器已经知道错在哪个文件，
  **不需要让 LLM 再推断一遍归因**（那正是它最容易编造的地方）
- A 层有硬失败时**不唤醒主理人**（`[未唤醒主理人]`）。让 LLM 复述编译器已经说清的话，
  只会更模糊、顺手编几个理由，并给它制造滥报机会
- 主理人谎称「编译失败」，并配了一个**必然非零退出的假 falsifier** 想骗过执行层 ——
  但 A4 锚点已 PASS，于是被判 `REFUTED`。**它骗得过执行层，骗不过事实底座。**

**场景 C · 甩锅 + 和稀泥 + 真人不可用**：无法归因的异议触发 T2 圆桌 →
圆桌产出没有行动项的「综合考虑、大家都有道理」决议 → **机械校验拒绝** → 真人不可用 →
第 3 层逃生：带债通过。受影响需求被标为 `ACCEPTED_WITH_DEBT`（不是 `met`），
并写出 `TECH_DEBT.md`，开头就写明「这些条目**没有被解决**，只是被明确记录后继续推进」。

**场景 D · 交叉质询：反驳当场执行，决议被机械证据否决**（唯一演示第 2 层逃生的场景）：

第 2 轮交叉质询时，`backend` 对 `test` 提出一个**真的会失败**的可执行反驳 ——
检查测试文件是否真的 import 了被测模块。机械主持**当场运行它**：

```
$ node -e "const fs=require('fs');const t=fs.readFileSync('tests/tasks.test.ts','utf8');
           process.exit(/import[^;]*api\/routes/.test(t)?0:1)"
→ 退出码 1  ⇒ sustained（反驳成立）
⇒ 机械事实：backend 的反驳被确证 → 问题在 test
```

随后产出的决议却习惯性地把责任推给 `pm`（「需求描述过于笼统，测试无法落地」）——
**与刚被执行的机械证据矛盾** → 决议被判无效 → 升级真人裁决。

这条演示回答的是「LLM 圆桌最容易在哪里翻车」：不是吵不起来，而是
**吵完之后产出一份无视证据、看起来很合理的纪要**。
机械事实的作用就是让这种纪要在生效前就被拦下。

> 注意这条 falsifier 是有**鉴别力**的：占位测试（不 import 被测模块）→ 退出码 1，
> 真实测试（import 了被测模块）→ 退出码 0。用 `node -e "process.exit(1)"` 这种
> 「保证失败」的命令也能跑出 `sustained`，但那什么都证明不了 ——
> 它只是把「反驳成立」四个字打印出来而已。

## 1. 它和 MetaGPT / ChatDev / AutoGen 有什么不同

参考项目的共同弱点，也是本项目的四个切入点：

| 已有项目的弱点 | AgentForge 的对应设计 |
|---|---|
| 角色间靠自然语言传递，理解偏差逐级累积，"我以为你懂了" | **接口即通信**：跨角色只有类型化工件（JSON Schema），schema 校验失败就等于通信失败，不给"理解偏差"留空间 |
| 审查者/QA 角色无问责，容易变橡皮图章；或在提示词压力下附和 | **机械裁判**：审查意见必须携带可证伪断言 + 真实证据引用；由确定性程序仲裁，不靠 LLM 互相说服 |
| 没有独立的、非 LLM 的事实裁决者，幻觉在角色间互相"确认" | **锚点链**：7 层检测，A 层全确定性（包真实性/符号存在/编译/测试/契约），B 层 LLM 判定必须引用真实存在的证据，否则判定作废 |
| 要么过早收敛，要么陷入死循环（liveness 无保证） | **推进保证**：三层死锁逃生（圆桌 → 真人裁决 → 带债通过），任何角色都无法让项目停死 |
| 对抗性提示词会导致审查者为了"体现价值"而滥报 | **问责账本**：把主理人的目标函数从"找茬数量"改成"找茬精度（precision）"，误报双倍扣额度，累计误报进观察期 |

## 2. 五个角色 + 一个裁判

| 角色 | 产出工件 | 权限 |
|---|---|---|
| **PM** | `Requirement[]`、`PRD`、`TaskGraph`、`Contract` | 可发布需求与契约，可冻结契约 |
| **前端** | `CodeModule(scope=web)`、组件级 `TestSuite` | 只读契约（冻结后），只写自己 scope 的代码 |
| **后端** | `CodeModule(scope=api)`、接口级 `TestSuite` | 同上 |
| **测试** | `TestSuite`、`TestReport` | 只读所有代码与契约，写测试；不参与实现 |
| **主理人** | `AnchoredReview`（锚定异议包） | **提异议 + 在额度内阻断**；不能写代码、不能改需求 |
| **机械裁判** | `GateResult`、`Arbitration` | **非 LLM**。仲裁异议成立/不成立，执行阻断、扣额度、升级圆桌 |

关键约束：**主理人没有最终裁判权**。它只能提出异议，成立与否由机械裁判依确定性规则判定。
人类用户拥有凌驾一切的**建议书（Directive）**权限。

## 3. 多层检测锚点（防幻觉）

A 层零 LLM、纯确定性；B 层有 LLM 参与，但每个结论必须锚定到 A 层事实。

| ID | 锚点 | 检查内容 | 层 |
|---|---|---|---|
| A1 | 包真实性 | 依赖包是否真实存在于 registry、版本是否存在、是否已废弃、是否与知名包构成 typo-squatting | A |
| A2 | 符号真实性 | `import { X } from 'pkg'` 中的 `X` 在真实类型定义里是否真的被导出（**比"包存在"强一级**） | A |
| A3 | 导入可解析 | 每个 import 能否解析到真实文件/模块 | A |
| A4 | 编译/类型 | `tsc --noEmit` 等真实编译器，产出结构化 diagnostics（文件/行/列/错误码） | A |
| A5 | 测试执行 | 真实跑测试，取退出码与覆盖率 | A |
| A6 | 运行时行为 | 真实启动服务 / e2e HTTP 探针 | A |
| A7 | 契约一致性 | 实现对冻结契约的符合性（OpenAPI / JSON Schema 校验真实响应） | A |
| B1 | 目标达成 | LLM 逐条需求判定，**每条必须给出指向真实存在的文件+行的 evidence**，否则该条作废 | B |
| B2 | 需求覆盖矩阵 | 需求 → 实现 → 测试 的映射，缺项直接暴露 | B |
| B3 | 对抗审查 | 主理人在 A 层全绿时仍可提语义质疑，但必须给出可执行 falsifier | B |

设计原则：**LLM 永远不是最终裁判**。LLM 的判定降级为"提议"，由确定性规则或真人确证。
详见 `docs/02-anchor-protocol.md`。

## 4. 主理人：对抗但不失控

用户的原始诉求是"摆脱 AI 倾向于同意的倾向"。本项目的补充是：

> **找茬的目标是"高精度找茬"，不是"多找茬"。**

如果只给主理人"必须挑错"的提示词，它会为了证明自己有用而编造问题 —— 这正是奖励黑客（reward hacking）。
所以我们同时做两件事：**改变它的目标函数**（prompt 里明说你的评分是 precision 不是 block 数，并把 precision 显示在 UI 上），
以及**用账本硬约束它**：

- 异议必须包含 `claim`（可证伪断言）+ `evidence`（真实文件+行/锚点ID）+ `falsifier`（可自动执行的检查，或必须由人回答的具体问题）+ `targetRole`
- 裁判三档裁决：`VALID`（真报，扣 1 额度）/ `UNFALSIFIABLE`（不可证伪，不阻断，转建议）/ `REFUTED`（误报，**扣 2 额度**并冻结下阶段阻断权）
- 复读机惩罚：同一 claim + 同一 evidence hash 再提一次，直接 REFUTED 且记误报
- 无法归因到具体角色 → 不阻断，**自动触发圆桌**（这正是一条圆桌触发条件）

**推进保证（liveness）—— 主理人永远无法让项目停死：**

1. 单阶段阻断尝试 ≥ 3 次 → 强制圆桌会议，主理人丧失该阶段阻断权
2. 圆桌 2 轮无决议 → 升级真人裁决
3. 真人不可用（无人值守）→ **带债通过**：写 `TECH_DEBT.md`，受影响需求标记 `ACCEPTED_WITH_DEBT`，项目继续推进，异议转入 backlog 而非 block
4. 全局预算：整项目阻断尝试上限 = `3 × 阶段数`，超出直接全局观察期

详见 `docs/03-host-accountability.md`。

## 5. 真人用户的建议书（Directive）

优先级：`USER_DIRECTIVE > FROZEN_CONTRACT > HOST_OBJECTION > ROLE_OPINION`

建议书类型：

- `requirement` — 改需求
- `constraint` — 加约束（例：不许引入某个库）
- `override` — 推翻某角色的某个决定
- `resume` — **解除当前阻断，强制推进**（打破死锁的终极手段）
- `hold` — 暂停流水线

建议书进入带 hash 的决策日志，机器人不得忽略或"重新解释"。

**关于 `constraint` —— 哪些约束真的会被强制校验**（这一点必须让用户看见）：

| 写法 | 行为 |
|---|---|
| 「不得引入 lodash」「只允许 leftpad-real」 | ✅ 编译成 deny/allow 列表 → **A1 锚点在门禁中强制校验**（同时检查 `package.json` 声明与代码导入）→ 违反即 FAIL 并派工单，验收条件里写明「这是用户约束，不可协商」 |
| 「代码风格要简洁」 | ⚠️ **不**强制校验。只作为上下文传给角色，也仍记入决策日志 |

控制台把两类**分开显示**，不会让你以为没生效的约束正在生效。
这是一个踩过坑才补上的区分：`constraint` 曾经是死代码，而文档却写着它「由 A1 强制校验」
—— 详见 `docs/07 §J1` 与 `docs/05 §2.3.1`。

## 6. 圆桌会议（唯一的自由通信场合）

触发条件（满足任一）：

- 某阶段主理人阻断尝试 ≥ 3 次
- 主理人**无法将该问题归因给具体角色**（`targetRole = UNRESOLVED`）
- 两个角色对同一契约/实现给出互相矛盾的产出
- 测试锚点连续失败且无人认领

规则：有议程、有证据、有产物、有轮数上限（2 轮）。产物必须是结构化的
`{归因, 决策, 行动项[{owner, 验收条件}], 契约变更}`，**禁止"和稀泥"决议**（裁判校验行动项非空且每条有 owner 与可验证验收条件）。

### 6.1 第 2 轮交叉质询：反驳当场执行

第 2 轮不是「再吵一轮」，而是**用可执行的反驳终结争议**。每条反驳都可以携带一个
`falsifier`，机械主持**立即运行它**，用执行结果而不是措辞来裁决：

| 结果 | 条件 | 后果 |
|---|---|---|
| `sustained` | 命令复现了反驳（非零退出 / 输出匹配） | 记为一条**机械事实** |
| `refuted` | 命令复现不出来 | **整条发言被丢弃**，且不进决议的输入 |
| `inconclusive` | 命令被安全策略拒绝 / 起不来 / 超时 | 不裁决、不产生事实、**不惩罚任何一方** |

`inconclusive` 不写成事实是刻意的：**「执行不了」不是「说错了」**。

被证伪的发言会从交给 LLM 生成决议的输入里剔除 —— 否则 LLM 会把它当成一个
平等的主张来「综合考虑」，而机械已经证明它是错的。

**质询对象由机械决定**，不由 LLM 决定：机械归因指向的角色优先；
没有归因时（典型的「不知道该怪谁」）改为**轮转配对**。

### 6.2 机械事实约束决议

有了当场执行的事实之后，决议多两条否决规则：

> **决议不得把责任归给一个机械证据已经证明它没问题的角色。**

> **也不得改口说「是需求/契约本身写得不好」** —— 机械证据证明的是
> 「实现与冻结契约不符」，推不出「契约是错的」；而改需求是**真人保留的权限**。

**这条规则的确切能力边界（诚实记录）**：`sustained` 证明的是
「反驳方给出的命令在当前工件上复现了」，它**不**证明「反驳方对责任的判断是对的」。
一个技术上真实但方向错误的 falsifier 同样会被记为 `sustained`，
从而把归因锁在错误的角色上。`SHARED` 是留给「方向不明」情形的出口；
要彻底解决需要把「反驳的逻辑方向」也变成可机械核验的，那超出当前设计能诚实承诺的范围。

### P4 之后的结构取舍：引擎零依赖 vs 控制台带工具链

`apps/web` **刻意不列入 npm/pnpm workspace**。原因有两个层面：

1. 技术上：根 `package.json` 声明 workspaces 后，npm 会拒绝在子目录安装（`ENOWORKSPACES`）
2. 架构上（更重要）：**引擎保持零依赖是真实优势** ——
   `node packages/orchestrator/src/cli.ts` 开箱即用，不需要装任何东西。
   不应该为了控制台把它牺牲掉。两者独立安装、互不影响。

### 技术选型

| 选择 | 理由 |
|---|---|
| **TypeScript 全栈** | 工件 JSON Schema 可直接复用为 TS 类型，前端零成本共用领域模型，「接口即通信」因此能被编译器部分强制 |
| **零运行时依赖** | 环境里 npm registry 不可达（三种镜像均超时），但这反而促成一个更好的架构决定：不引 zod/ajv，自己写 JSON Schema 校验子集；测试用 Node 内置运行器。**只需要 Node ≥ 24 就能跑，不需要 `npm install`** |
| **Node 原生类型剥离** | 直接用 `node xxx.ts` 运行，不需要构建步骤与 `tsc` 编译链路。约定：不使用 `enum`/`namespace`/参数属性，import 带 `.ts` 扩展名 |
| **JSON 文件存储 + jsonl 日志** | 可 git diff、人类可读、离线回放。规模大了再引入索引层，接口不变 |
| **子进程输出走临时文件** | 受限环境无法打开命名管道，管道式 stdio 直接 EPERM。重定向到文件再读回，任何环境都能拿到完整输出与真实退出码 |
| **事件驱动 + 不可变事件** | 前端重连不丢状态；整个 run 可回放 |

> 说明：`pnpm-workspace.yaml` 与各包的 `package.json` 已就位，网络可用时可随时 `pnpm install`
> 引入 `typescript`（用于 A4 锚点的权威类型检查）与 `vitest`，接口不变。

### 沙箱环境的两条技术约束（已验证，附绕行方案）

1. **`node --test <dir>` 不可用**：该模式为每个测试文件 spawn 子进程并走管道 stdio，
   而受限环境无法打开命名管道（EPERM）。
   → 改为**单进程内导入全部 `*.test.ts`**（`scripts/run-tests.ts`）。
2. **`child_process.exec` / 默认 `stdio: 'pipe'` 不可用**：同上原因。
   → 子进程输出改为**重定向到临时文件再读回**（`packages/core/src/exec.ts`），
   真 HTTP 探针与 tsc 诊断解析都依赖它。

两处绕行在任何环境下都成立，不是针对沙箱的特例。

### 编码阶段发现的规格修正（30+ 处）

这些修正记录在**实现笔记**里 —— 那份文档刻意不随仓库发布（理由见 `.gitignore` 里的说明）。
下面摘出**最严重的一条**，因为它的形态比结论本身更重要：

> 语义验证因 `rationale` 的 `minLength: 5` 失败 → 提议为 null → B1 诚实报 `SKIPPED`
> → Gate 只把 `FAIL`/`INVALID_EVIDENCE` 当硬失败 → **一路 ADVANCE 到「完整交付」**，
> 而「目标是否达成」从未被验证过。
>
> 链条里每一步单独看都对，合起来却违反了写在文档最前面的不变量「`SKIPPED ≠ PASS`」。
> 修法是在 Gate 引入 `blockingGaps()` —— 每个判定点都要问一次
> 「这里的未知会不会被下游当成通过？」。

其他代表性发现：
- **未开始 ≠ 已失败**：B2 曾在 PLANNING 阶段因「需求还没有测试覆盖」判 FAIL —— 那时一行代码都没写
- **检查的时机是设计的一部分**：同一个检查放在错误的阶段，就从「严格」变成「噪音」
- **不能用昨日的事实审判今天的提交**：修复后重进 REVIEW，语义验证与对抗审查必须重跑
- **失败必须可记录**：和稀泥决议曾被工件 schema 直接拒收，导致失败的圆桌无法留证
- **代理指标要极其谨慎**：字数约束误伤合法输入，而它想守的门已经有证据核验在把守
