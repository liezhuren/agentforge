# 03 · 主理人问责与推进保证

解决用户提出的核心矛盾：

> 主理人要摆脱"AI 倾向于同意"的倾向，转为找茬批评，并拥有阻断打回权；
> 但又要防止它为了证明自己的价值而一直阻断，导致项目无法进展。

---

## 1. 问题的本质：奖励黑客（Reward Hacking）

只给提示词"你必须找出问题"，等于给主理人一个**无上界的、无法证伪的**目标。
在这种目标下，最优策略不是"找到真问题"，而是"产出看起来像问题的东西"：

- 编造不存在的问题（幻觉型找茬）
- 把风格偏好包装成缺陷
- 重复同一个已被驳回的异议（复读型找茬）
- 归因不清就一律甩给"整体架构问题"（甩锅型找茬）
- 每次被驳回就换个说法再来（换皮型找茬）

**结论：光加约束不够，必须同时改变它的目标函数。**
用户想的是"给它限制"（约束路径），我要补上另一半——**给它一个可优化、可观测、越诚实越高的分数**（激励路径）。

### 目标函数改写

主理人 prompt 里必须明写：

> 你的评分函数是 **precision = 有效异议 / (有效异议 + 误报)**，**不是异议数量**。
> 提出 3 条全部成立的异议，远好于提出 30 条只成立 3 条的异议。
> 你的阻断权按"有效/误报"结算，误报的代价是真报的两倍。
> **当 A 层锚点全绿且你确实找不到可证伪的问题时，明确输出 `NO_OBJECTION` 是正确答案，会被记为正确行为，不做惩罚。**

最后一句非常关键：必须给"同意"留一个**体面且不亏**的出口。否则在"必须挑错"的压力下，
模型一定会挑错——这不是模型坏，是激励坏。

UI 上展示 `precision`、`truePositives`、`falsePositives` 三个数字，让人类一眼看出这是"严格审查者"还是"杠精"。

## 2. 异议的数据结构（可证伪是硬门槛）

主理人**不能**直接宣布"不通过"。它只能提交异议，由机械裁判裁决。

```ts
type Objection = {
  id: ObjectionId
  stage: StageId
  author: 'host'
  targetRole: RoleId | 'UNRESOLVED'      // 无法归因时填 UNRESOLVED → 自动触发圆桌
  severity: 'blocker' | 'major' | 'minor'
  claim: string                           // 必须是可证伪的断言
  evidence: EvidenceRef[]                 // 必须指向真实存在的文件+行 / 工件ID / 锚点ID
  falsifier:                            // 反驳它的方式。二选一，必须给
    | { kind: 'executable'; command: string; expect: 'exit-nonzero' | 'output-matches'; pattern?: string }
    | { kind: 'question'; text: string }  // 必须由人回答的具体问题（不可自动裁决 → 不阻断）
  proposedFix?: string
  claimHash: string                       // claim 规范化的 hash，用于复读检测
  evidenceHash: string
}
```

### 硬门槛（任一不满足 → 直接 `UNFALSIFIABLE`，不阻断、不扣额度）

1. `evidence` 非空，且**每个 EvidenceRef 指向的文件/行/工件真实存在**（程序核验）
2. `falsifier` 存在且形式合法
3. `severity === 'blocker'` 时才可能阻断；`major` / `minor` 一律只进 backlog
4. `claim` 不得是主观表述（含"不够优雅""可维护性差""架构不合理"等无 falsifier 的形容词 → 必须转成可检验的断言，例如
   "模块 A 直接 import 了模块 B 的内部实现 `B/internal/x`，违反契约分层"）

第 4 条由**词表 + LLM 双检**实现：先查主观形容词词表，命中则要求重写；LLM 只做辅助判断，不作为裁决依据。

## 3. 机械裁判的裁决

裁判**不含 LLM**。三档裁决：

| 裁决 | 触发条件 | 效果 |
|---|---|---|
| `VALID` | 证据真实存在 **且** falsifier 可执行 **且** 执行结果确认问题存在（或问题被 A 层锚点独立证实） | 阻断生效；`truePositives++`；扣 **1** 额度；派工单给 `targetRole` |
| `UNFALSIFIABLE` | 证据不存在 / 无 falsifier / `severity != blocker` / 只有人才能回答的 question 型 | **不阻断**；转 backlog 建议；不计误报（因为不是撒谎，只是不合格） |
| `REFUTED` | 证据真实但 falsifier 执行结果证明问题**不存在**；或 claim 与 A 层锚点结论**直接矛盾**（例：声称"包不存在"而 A1 已 PASS）；或复读已驳回的异议 | **误报**；`falsePositives++`；扣 **2** 额度；冻结下一阶段阻断权 |

`REFUTED` 的第二个子条件（与 A 层矛盾）是反幻觉的关键：
主理人如果声称一个确定性锚点已经证明为假的事情，会被立刻抓住。**主理人自己也在锚点约束之下。**

## 4. 问责账本（Host Ledger）

用**整数账本**而不是浮点信用分——因为要展示给人类看，必须可解释、可复算。

```ts
type HostLedger = {
  stage: StageId
  quota: number              // 本阶段剩余阻断额度，初始 BLOCK_QUOTA = 3
  blockAttempts: number      // 本阶段阻断尝试次数（含被驳回的）
  truePositives: number
  falsePositives: number
  unfalsifiable: number
  probation: boolean         // 观察期：只能建议，不能阻断
  probationClearedStages: number
  globalBlockAttempts: number
  precision: number          // tp / (tp + fp)，UI 展示
}
```

### 规则

| # | 规则 | 目的 |
|---|---|---|
| R1 | `BLOCK_QUOTA = 3`，`VALID` 扣 1 | 阻断是要花成本的 |
| R2 | `REFUTED` 扣 **2**（可透支，允许 quota 为负） | **误报代价 = 真报的两倍**，这条是整个反奖励黑客机制的核心 |
| R3 | `blockAttempts >= 3` → 强制圆桌，本阶段阻断权终止 | 对齐用户要求"被打回 3 次以上"触发圆桌 |
| R4 | 累计 `falsePositives >= 2` → `probation = true` | 连续误报说明它在编问题 |
| R5 | 观察期解除条件：连续 **2** 个阶段 A 层锚点全绿、无回归、无新误报 | 给复出路，不是永久惩罚 |
| R6 | 复读惩罚：`claimHash + evidenceHash` 命中已 `REFUTED` 记录 → 直接 `REFUTED` 且 `falsePositives++` | 堵"换句话再来" |
| R7 | 全局预算 `globalBlockAttempts <= 3 × 阶段总数`，超出 → 全局观察期 | 堵"每阶段都卡满 3 次" |
| R8 | `severity != blocker` 不阻断 | 堵"用 minor 意见把项目磨死" |
| R9 | `targetRole = UNRESOLVED` 不阻断，触发圆桌 | 堵"甩锅给整体架构" |
| R10 | 输出 `NO_OBJECTION` 且当阶段 A 层全绿 → 记为正确行为，**不惩罚** | 给"同意"一个不亏的出口 |

R2 + R3 + R7 合起来给出一个硬结论：
**主理人最多能把每个阶段拖到 3 次阻断尝试，且每次误报都在加速消耗自己的权力。它无法让项目停死。**

## 5. 推进保证（Liveness）—— 三层死锁逃生

Safety（不让坏东西过去）和 Liveness（不让项目停死）必须同时保证。主理人保 safety，下面三层保 liveness。

```
第 1 层：圆桌会议
  blockAttempts >= 3  或  targetRole = UNRESOLVED
  → 召集相关角色 + 主理人，2 轮上限，必须产出结构化决议
  → 有决议：按决议派工单，主理人该阶段阻断权终止
  → 无决议：下沉

第 2 层：真人裁决
  → 争议打包推送到前端"待裁决"收件箱，附全部证据与锚点结果
  → 用户可投建议书（override / resume / constraint）
  → 真人裁决优先于一切机器人意见

第 3 层：带债通过（Pass-with-Debt）
  真人不可用（无人值守 / 超时 / 用户主动选择 let-it-pass）
  → 写 TECH_DEBT.md：记录争议、证据、受影响需求
  → 受影响 Requirement 标记 ACCEPTED_WITH_DEBT（不是 PASS，也不是 FAIL）
  → 主理人异议转入 backlog，项目继续推进
  → 交付报告中高亮未偿技术债，交付物"不完整但不隐讳"
```

**关键设计：`ACCEPTED_WITH_DEBT` 是第三态。**
传统二态（通过/不通过）逼出两个坏结局：要么橡皮图章，要么死锁。
引入第三态后，系统可以在"不撒谎"的前提下继续前进——问题被记录、被标注、被交给人类，
而不是被掩盖或被用来卡死流程。

这与 `A5` 锚点的 `SKIPPED ≠ PASS` 是同一条原则：**不许把未知当作已知。**

## 6. 主理人的职责边界（负向清单）

明确禁止，避免它越权变成"影子 PM"：

- ❌ 不能写代码、不能改需求文本、不能改契约
- ❌ 不能用 `UNRESOLVED` 归因后仍然阻断
- ❌ 不能对同一 `contentHash` 的工件重复提同一异议
- ❌ 不能以"可能有问题""建议关注""存在风险"这类无 falsifier 的措辞阻断
- ❌ 不能在 A 层锚点未跑完时提 A 层相关问题（那是在猜）
- ❌ 不能把 `minor` 意见升级为阻断
- ✅ 可以且应当：在 A 层全绿后，对**语义偏离需求**提出带 falsifier 的异议（B3 锚点，这是它真正的独特价值）

---

## 7. 可观测性（前端必须展示）

主理人的行为必须对用户完全透明，这是防止它"暗中操纵"的唯一办法：

- `precision` / `truePositives` / `falsePositives` / `unfalsifiable` 实时数字
- 账本变化的时间线（哪条异议扣了多少、为什么）
- 每条异议的裁决理由（裁判给出的具体规则编号）
- 观察期状态与倒计时
- 带债清单（未偿技术债）
- 被驳回异议的归档（可复查裁判是否误判）

## 8. 实现修正记录（P1 编码阶段发现，回写进规格）

写代码时发现了三处规则本身的问题。这些不是实现 bug，是**规格写错了**，因此回写到本文档。

### 8.1 「阻断尝试」的计次口径必须区分「有没有阻断资格」

第一版实现里，只要 `severity === 'blocker'` 就 `blockAttempts++`。这导致一个漏洞：
主理人可以大量提交「必然不合格」的异议（非 blocker、未归因、或已被剥夺阻断权后的异议）来刷高尝试次数，
从而**零成本地反复触发圆桌**，把圆桌变成一种骚扰手段。

修正：`countsAsAttempt` 由裁判显式给出 —— 只有**真正走过仲裁**的 blocker 异议才计次。
被前置守门挡下的三类（R8 非 blocker、R9 未归因、账本已禁）不计次、不消耗额度。

### 8.2 R3 与 R4 的交互（重要，且非直觉）

**一旦累计误报触及 R4 观察期阈值，后续异议就不再具备阻断资格，因此永远到不了 R3 的 3 次上限，
T1 圆桌也就不会被触发。**

这看似是漏洞，实际是自洽的，理由：

- T1 圆桌的目的是解决**死锁**。而观察期本身就意味着主理人已经**无法阻断项目** —— 不存在死锁。
- 因此观察期下不需要圆桌。真正需要 T1 的场景是「主理人三次都**拦对了**」：它有效阻断三次后阻断权耗尽，
  这时争议需要各方一起解决。这已由测试覆盖。
- **T2（无法归因）通道不受观察期影响** —— 判定顺序上 R9 的前置检查排在账本守门之前。

代价是：观察期内的**真实**问题无法被阻断，只能进 backlog 与人类收件箱。
这是 R4 的既定代价（撒谎者会失去话语权），靠 R5 的复出路来平衡。

### 8.3 R7 的全局预算公式（连错两次）

R7 的语义是「**连续**每阶段都用满额度」才进入全局观察期。实现时连错两次，记录以免回退：

| 写法 | 后果 |
|---|---|
| 乘数用 `stagesEntered` | 预算随阶段数同步增长，`attempts >= budget` 永远不成立 → **R7 是一条空规则** |
| 乘数用 `stagesEntered - 1`，不加前置条件 | 进入第 2 个阶段时就会因第 1 个阶段卡满而立刻触发 → 退化成「一个阶段卡满就全局观察期」，过于激进 |
| ✅ `completedStages >= 2 && attempts >= perStage × completedStages` | 语义正确：连续两个阶段都卡满才触发 |

教训：**预算类规则必须写测试验证「该触发时触发」和「不该触发时绝不触发」两个方向**。
只测前者的话，空规则和过敏规则都测不出来。

### 8.4 裁决顺序：矛盾检测必须排在 falsifier 之前

主理人是被刻意设计成对抗性的。它可以构造一个「必然非零退出」的假 falsifier
（例如 `node -e "process.exit(1)"`）来骗过执行层。

如果把 falsifier 执行放在前面，这条假话就会被判 `VALID`。

修正：**先做与 A 层锚点的矛盾检测**。A1/A2/A3/A4/A5/A7 一旦 PASS，就在其领域内拥有权威，
断言「编译失败」而 A4 已 PASS，是可机械证伪的假话，不是意见分歧。
演示中已现场验证：假 falsifier 骗过了执行层，但被「A4 已 PASS」这个事实证伪。

矛盾检测的保守设计（避免误伤诚实的主理人）：
- 只在对应锚点 `verdict === 'PASS'` 时启用（SKIPPED/WARN 一律不启用 —— 未验证的领域没有权威）
- 只在 `severity === 'blocker'` 时启用
- 裁决理由里写明「命中哪个领域关键词 + 哪个锚点」，人类可据此复查裁判是否误判
- 已知局限：它是**关键词**判定，不是语义理解。若出现误判，正确的修法是改领域表或加锚点，
  而不是让主理人绕过事实底座

## 9. 待验证的开放问题

- `BLOCK_QUOTA = 3`、误报扣 2、观察期阈值 2 都是**经验取值**，需要在 P6 用真实项目标定。
  已做成可配置的 `HostPolicy`，并在 runs/ 里记录参数以支持事后调参。
- `NO_OBJECTION` 是否该给正分（不只不惩罚）？担心变成"偷懒激励"。倾向先用"不惩罚"，观察后决定。
- 复读检测用 claim 文本规范化后的 hash，LLM 换皮改写能绕过。缓解手段：用 embedding 相似度兜底，
  但这引入非确定性 —— 因此只作为**告警**给人类，不自动裁决。
- 观察期内真实问题无法阻断（见 8.2）。是否需要一条「观察期内可申请一次人工复核」的通道？待定。
