但说不出它的**检出率**与**误报率**。而防幻觉机制的价值完全由这两个数字决定。

## 方法

每个样本在一个**独立临时工作区**里构造：写项目文件、造已安装的假 npm 包（含真实 `.d.ts`）、
发布工件，然后只运行该样本关心的锚点，最后把实际判定与**事先声明的期望**比对。

判定规则刻意保守：

| 结果 | 含义 |
|---|---|
| `TP` | 期望被抓到，确实抓到（严重度符合） |
| `FN` | 期望被抓到，但没报硬失败 → **漏报** |
| `FP` | 干净对照组里出现了硬失败 → **误报** |
| `TN` | 干净对照组里无任何硬失败 |
| `严重度不符` | 抓到了，但比期望更重（例如期望 WARN 实际 FAIL） |

**为什么每个注入样本都配对照组合**：只测「能不能抓出问题」毫无意义 ——
一个永远返回 FAIL 的锚点检出率是 100%。必须同时测「它会不会把正确的东西判成错的」。
在锚点这事上误报和漏报**同样有害**：
漏报 → 幻觉通过；误报 → 把诚实代码判成幻觉，角色被派去修一个不存在的问题
（浪费一轮，还可能把对的改成错的）。

## 首轮 100% 通过时发生了什么

第一版靶场（36 个样本）跑出来是 **0 误报 0 漏报、检出率 100%**。
我没有把它当成好消息 —— **「一次就全过」本身就是可疑信号**：
它通常意味着样本太贴合被测对象的强项（样本是我写的，我很清楚锚点是怎么实现的）。

于是主动加了 3 个**对抗性样本**去攻它的弱点，其中两个各抓到一个真实缺陷：

| 样本 | 攻的是什么 | 结果 |
|---|---|---|
| `A5-05-unparseable-output` | 测试命令退出 0，但输出里没有任何可解析的计数 | **抓到**：A5 原本报 `PASS` —— 它其实什么都没验证到。退出码 0 不等于测试通过（脚本可能被 `\\|\\| true` 吞掉、可能压根没跑到测试）。已修为 `WARN(test-counts-unparsed)` |
| `A7-07-endpoint-only-in-comment` | 端点只写在注释里（`// TODO: 实现 /api/tasks`） | **抓到**：A7 的端点覆盖检查是子串匹配，注释里的路径同样是子串，于是「一行都没实现」被判成已实现。已修为先剥注释再匹配 |
| `A7-08-clean-parameterized-path` | 反向验证：契约声明 `/api/tasks/{id}`，前端写 `` fetch(`/api/tasks/${id}`) `` | **通过**：确认归一化把它们视作同一路径，没有引入误报 |

这两处修完，靶场从 36 个样本长到 39 个，仍然是 0 误报 0 漏报 ——
但现在的 100% 比第一版的 100% 可信一些，因为它至少经过了**一次主动的攻击**。
当然，攻击的力度仍然受限于我能想到什么。

## 这份报告**不能**说明什么

1. **样本是我手写的。** 它测的是「锚点能不能抓出我想到的这类幻觉」，
   **不是**「锚点能不能抓出真实世界里的所有幻觉」。
   我没想到的幻觉形态，这份报告里必然缺席 —— 这是自出题自答的固有局限。
   上面那段「主动加对抗样本」只是部分缓解，不能消除它。
2. **A1 的远端核实未纳入。** 靶场离线运行，A1 只能做本地检查（命名规则 / typo 距离 / 依赖白名单）。
   「包在 registry 上是否真实存在」这一项需要联网，届时才会被真正检验。
   **这是当前最大的一块未覆盖区域**：编造一个名字合法、也不像知名包的假包，本靶场抓不到。
3. **A4/A5/A6 用的是确定性的假命令**（`node -e`）而不是真 tsc / 真测试运行器。
   这保证了靶场快且可复现，代价是「解析真实工具输出」这部分能力没有被这里的样本覆盖 ——
   那部分由 P6 的 `real-app` 场景（真 tsc / 真 node --test）覆盖。
4. **样本量小。** 每个锚点的正例数是个位数（A3 只有 1 个），召回率的粒度很粗：
   一个样本就是 50–100 个百分点。这些数字适合用来发现「某个锚点整体失效」，
   **不适合**用来做精细调参。
5. **没有测量「幻觉的变体」**。真实的模型幻觉往往更隐蔽：
   包名对、符号对、但语义用错（例如把 `padLeft` 用在需要 `padRight` 的地方）。
   这类错误 A1–A3 都抓不到，A4 也只在类型不匹配时才抓到 ——
   它属于 B1/B3 的语义判断范围，而 B 层依赖 LLM，本靶场只喂了脚本化的提议。
