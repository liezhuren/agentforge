# 01 · 总体架构

---

## 1. 分层

```
┌───────────────────────────────────────────────────────────────┐
│  apps/web · React 控制台                                        │
│  流水线视图 / 锚点红绿灯 / 主理人账本 / 异议收件箱 /              │
│  建议书编辑器 / 圆桌纪要 / 工件浏览器 / 回放播放器                │
└──────────────────────────┬────────────────────────────────────┘
                    WebSocket(事件流) + HTTP(命令)
┌──────────────────────────┴────────────────────────────────────┐
│  packages/server · API 层                                      │
└──────────────────────────┬────────────────────────────────────┘
┌──────────────────────────┴────────────────────────────────────┐
│  packages/orchestrator · 编排核心【无 LLM 逻辑】                 │
│  ┌────────────┐ ┌──────────┐ ┌───────────────────────────┐   │
│  │ 阶段状态机  │ │ Gate 门禁 │ │ 机械裁判 MechanicalJudge   │   │
│  └────────────┘ └──────────┘ └───────────────────────────┘   │
│  ┌────────────┐ ┌──────────┐ ┌───────────────────────────┐   │
│  │ 派工调度器  │ │ 圆桌主持  │ │ 账本 HostLedger / 死锁逃生  │   │
│  └────────────┘ └──────────┘ └───────────────────────────┘   │
└───────┬───────────────────────────────────────┬───────────────┘
        │                                       │
┌───────┴────────────┐              ┌───────────┴───────────────┐
│ packages/roles     │              │ packages/anchors          │
│ 五角色 prompt +    │              │ A1–A7 确定性检查器         │
│ 输出 schema        │              │ B1–B3 语义锚(带证据核验)    │
└───────┬────────────┘              └───────────┬───────────────┘
        │                                       │
┌───────┴───────────────────────────────────────┴───────────────┐
│  packages/llm · Provider 抽象 / 模型注册表 / 能力探测 /          │
│                 成本预算 / 确定性回放                           │
└──────────────────────────┬────────────────────────────────────┘
                           │
┌──────────────────────────┴────────────────────────────────────┐
│  packages/core · 领域模型 + 工件存储 + 事件总线 + 哈希链          │
└───────────────────────────────────────────────────────────────┘
```

**关键分层原则：`orchestrator` 里没有 LLM 调用。**
编排逻辑全部是确定性代码。LLM 只出现在 `roles`（产出工件）和 `anchors` 的 B 层（产出提议）。
这条约束让整套流程可测试、可回放、可推理——如果让 LLM 决定"下一步做什么"，系统立刻变成不可调试的黑箱。

## 2. 阶段状态机

```
INTAKE ──► PLANNING ──► CONTRACTING ──► BUILDING ⇄ REVIEW ──► DELIVERED
   │            │             │              │  ↑
   │            │             │              ▼  │
   └────────────┴─────────────┴────────► ROUNDTABLE
                                             │
                                             ▼
                                        ARBITRATION ──► (人类裁决)
                                             │
                                             └──► PASS_WITH_DEBT ──► BUILDING / DELIVERED
```

| 阶段 | 做什么 | 主要锚点 |
|---|---|---|
| `INTAKE` | 用户需求 → 原子化 `Requirement[]`（R-001…），每条必须**可验证** | B2 预检：不可验证的需求被打回 |
| `PLANNING` | PM 产出 PRD + TaskGraph | B1（PRD 是否覆盖全部需求） |
| `CONTRACTING` | 产出并冻结 Contract | A7 自洽性 + B1 |
| `BUILDING` | 按 TaskGraph 派工单，角色产出 CodeModule | A1–A6 |
| `REVIEW` | 主理人审查 + 裁判裁决 | A7 + B1/B2 + B3 |
| `ROUNDTABLE` | 争议协商 | — |
| `ARBITRATION` | 真人裁决 | — |
| `DELIVERED` | 交付 + 未偿技术债清单 | 全量最终锚点 |

`BUILDING ⇄ REVIEW` 是主循环。每次循环的产物是一个 `GateResult`，`nextAction` 由机械裁判给出：

```ts
type NextAction =
  | { kind: 'RETRY_ROLE'; target: RoleId; orders: WorkOrderId[] }
  | { kind: 'ROUNDTABLE'; trigger: 'T1'|'T2'|'T3'|'T4'|'T5' }
  | { kind: 'ARBITRATE_HUMAN'; bundle: EscalationBundleId }
  | { kind: 'ADVANCE'; to: StageId }
  | { kind: 'PASS_WITH_DEBT'; debt: DebtRecordId }
```

**`nextAction` 由程序计算，不由 LLM 决定。** 这是"机械裁判"这个词的落地方式。

## 3. 一次 BUILDING 循环的完整数据流

```
1. 调度器从 TaskGraph 取就绪任务 → 生成 WorkOrder(绑定 contractHash)
2. 角色适配器: 组装上下文（只含该角色有权读的工件 + 契约类型 + 相关锚点失败详情）
              → 调 LLM（schema 约束输出）
              → 解析 → schema 校验 → 失败则结构化重试（最多 N 次）
              → 发布 Artifact（带 contentHash）
3. 锚点运行器: 对受影响的工件跑 A1–A7
              → 每个结果绑定 contentHash 写入 anchorChain
              → 任何 hash 变化使旧锚点 STALE
4. Gate:
   a. 收集 hardFailures（A 层 FAIL）
   b. 若有 hardFail → 机械归因 → 直接 RETRY_ROLE（不打扰主理人）
   c. 若 A 层全绿 → 调用主理人（B3），收 Objection[]
   d. 机械裁判逐条裁决 → 更新账本
   e. 计算 nextAction（含死锁逃生判定）
5. 广播事件 → 前端更新
6. 记录 llm run 到 runs/（可回放）
```

第 4c 步的设计要点：**主理人只在 A 层全绿之后才被唤醒。**
编译器已经能说清的问题，不要让 LLM 去重复描述一遍（它只会描述得更模糊，并顺手编几个理由）。
这既省钱，又砍掉了主理人绝大多数滥报机会。

## 4. 包职责

| 包 | 职责 | 明确不做 |
|---|---|---|
| `core` | 领域模型（角色/工件/异议/账本/建议书）、工件存储、哈希链决策日志、事件总线、JSON Schema 定义与 TS 类型 | 不调 LLM、不做 IO 副作用决策 |
| `llm` | Provider 抽象（OpenAI 兼容 / Ollama 等）、模型注册表、能力探测（strict json / tool calling）、重试与修复解析、token 成本预算、调用记录与回放 | 不含角色语义 |
| `anchors` | A1–A7 检查器、B1–B3 语义锚（含证据核验器）、锚点注册表与依赖排序 | 不做编排决策 |
| `orchestrator` | 状态机、Gate、机械裁判、账本、派工调度、圆桌主持、死锁逃生 | **不含 LLM 调用** |
| `roles` | 五角色的 system prompt、输出 schema、上下文装配策略 | 不做校验（交给 core schema） |
| `server` | HTTP 命令接口 + WebSocket 事件流 | 不含业务逻辑 |
| `apps/web` | 控制台 UI，事件投影 | 不持有真相 |

## 5. 技术选型与理由

| 选择 | 理由 |
|---|---|
| **TypeScript 全栈** | 环境已具备 Node 24 / pnpm 11（Python 不可用，仅 Store 占位符）。更重要的是：工件 JSON Schema → TS 类型 → 前端共用，让"接口即通信"能被编译器部分强制 |
| **pnpm workspace** | 包边界清晰，`core` 被所有包依赖，天然防止循环依赖 |
| **JSON 文件存储 + jsonl 日志** | 可 git diff、人类可读、离线回放。规模大了再引入索引层，接口不变 |
| **TS Compiler API 做 A2/A4** | A2（符号真实性）必须读真实类型定义，只有 TS 自身能给出权威答案；A4 需要结构化 diagnostics 而非解析 stdout |
| **事件驱动 + 不可变事件** | 前端重连不丢状态；整个 run 可回放 |
| **WebSocket 而非轮询** | 编排过程长（分钟到小时级），需要实时可观测与人类即时介入 |

## 6. 全局不变量（Invariants）

这些是系统的"宪法"，任何实现都不得违反：

1. **LLM 永远不是最终裁判。** LLM 只产出工件或提议，裁决由程序或人类做出。
2. **任何 PASS 都必须追溯到不依赖 LLM 的事实。**
3. **角色之间不存在未记录的共识。** 共识要么在工件 schema 里，要么在决策日志里。
4. **`SKIPPED` ≠ `PASS`。** 未运行的检查不得当作通过。
5. **锚点结果绑定内容 hash。** 内容变了，绿灯立刻失效。
6. **人类可以推翻任何机器人；但不能用"意见"推翻确定性事实。**
7. **主理人无法让项目停死。** 三层逃生永远可达。
8. **`orchestrator` 中不出现 LLM 调用。**
9. **历史 append-only。** 决策日志只增不改，哈希链防篡改。

## 7. 本架构对用户原方案的补充（摘要）

| 用户的原始想法 | 我的补充 | 理由 |
|---|---|---|
| 导包检查 | + A2 符号真实性、typo-squatting 检测、deprecated 检查 | "包存在"是弱检查，幻觉主要发生在符号层 |
| 编译检查 | + 结构化 diagnostics 直接机械归因 | 可省掉主理人 80% 的归因争议 |
| LLM 检测目标符合性 | + evidenceRefs 强制核验，核验失败判定作废；LLM 降级为"提议" | 防止 LLM 顺着自己的幻觉确认自己 |
| 主理人阻断权 + 限制 | + 目标函数改为 precision；误报双倍扣额；观察期；复读惩罚；全局预算 | 光加约束会被绕过，必须改激励 |
| 阻断 3 次 / 归因不清 → 圆桌 | + T3 契约冲突、T4 机械归因失灵、T5 契约变更僵局 | 补上另外三类真实僵局 |
| 圆桌会议 | + 结构化决议 + 反和稀泥机械校验 + 2 轮上限 | LLM 圆桌最典型的失败是产出"什么都没解决"的漂亮纪要 |
| 真人建议书 | + 五类型 + 优先级 + 不可重新解释 + hold 刹车 | 显式化才能防止 LLM 稀释用户意图 |
| 角色间通信只有接口 | + 写权限矩阵 + 契约冻结 hash + STALE 自动重跑 | 把口号变成可强制执行的规则 |
| — | + 确定性回放（runs/） | 没有回放就无法区分"模型问题"与"编排问题" |
| — | + `ACCEPTED_WITH_DEBT` 第三态 | 二态（通过/不通过）必然导致橡皮图章或死锁 |
