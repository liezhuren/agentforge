# 06 · 路线图

原则：**先让闭环在无网络下跑通，再接真 LLM。**
理由：多智能体系统最难调试的不是模型，而是编排。如果第一版就依赖真 LLM，每次失败都无法区分
"模型不行"还是"编排有 bug"，会因为不确定性和成本而陷入泥潭。

> 本文档曾被多轮增量编辑改乱（P2/P3/P6 各出现两份互相矛盾的章节），已重写。
> 教训见 `docs/07`：**文档和代码一样会积累结构性债务**，而路线图是读者最先看的那一页。

## P1 · 领域核心 + Mock 闭环（✅ 完成）

目标：**不联网、不花钱，完整跑通一次 `INTAKE → DELIVERED`，包含一次主理人阻断、一次裁判裁决、一次圆桌、一次带债通过。**

已交付：

- `packages/core` — 领域模型、零依赖 JSON Schema 校验器 + 全部工件 schema、
  工件存储（不可变 + 版本链 + 写权限矩阵 + schema 门禁 + 锚点链 hash 绑定）、
  事件总线、append-only 哈希链决策日志、子进程捕获（文件重定向 + 命令安全闸）、
  **契约 → TS 类型代码生成**（确定性，不经 LLM）
- `packages/anchors` — A1–A8 真实实现、B1–B3（LLM 提议 + 确定性证据核验）、运行器与权威度标注
- `packages/orchestrator` — 问责账本 R1–R10、机械裁判（三档裁决 + 与锚点矛盾检测 + 复读惩罚）、
  Gate 门禁 + `blockingGaps` 不变式检查、阶段状态机、圆桌会议（T1–T5 + 反和稀泥校验）、
  三层死锁逃生（圆桌 → 真人 → 带债通过）
- `packages/llm` — Provider 接口、MockProvider（脚本 + 幻觉注入 + 调用计数）
- `packages/roles` — 五角色 system prompt、读权限矩阵、LLM 运行器（schema 结构化重试）、语义验证器
- **89 个测试**全绿；两个演示脚本

**验收用例（全部已自动化）**：

| # | 场景 | 期望 |
|---|---|---|

| 3 | mock 注入真实包的不存在符号 | A2 FAIL(unknown-export) → 工单归因 backend |

## P2 · 真 LLM 接入（✅ 完成）

已交付：

- `OpenAiCompatProvider`（OpenAI / DeepSeek / Moonshot / 通义 / OpenRouter / vLLM / LM Studio）
  与 `OllamaProvider`（本地模型，原生 `format` 字段强约束）
- **能力探测**：strict → json-mode → prompt-only 三级降级，逐级留证并缓存；
  **严格区分「端点不可达/凭据错误」与「端点不支持某功能」** ——
  前者是致命问题、不降级，后者才降级
- **严格模式 schema 兼容转换**（可选字段→required+nullable、oneOf→anyOf、剔除不支持的约束），
  且服务端放宽的同时**客户端仍按原始 schema 校验**
- **JSON 修复链**（围栏 / 括号平衡提取 / 尾随逗号），修复痕迹留在 `parseError` 里
- **重试策略**：429/5xx 指数退避并尊重 `Retry-After`；其他 4xx 不重试（避免烧钱并掩盖真错误）
- **成本预算**（`BudgetTracker` + `BudgetedProvider`，按角色/全局限额，stop 或 warn）
- **离线回放**（`JsonlRunRecorder` + `ReplayProvider`，FIFO 队列匹配，遇未录制分支即报错）
- **配置层**（`agentforge.config.json`，每角色独立绑定 provider/model/温度，支持 `${ENV_VAR}`，
  错误一次性列清）
- `cli-run.ts`：`init` / 真实 run / `--replay` / `--verbose`

**验证方式**：主用**本地假的 OpenAI 兼容服务器**（真 HTTP、真 socket、真状态码、真超时）——
429 重试、拒绝 json_schema、超时、200 里塞 error 这些错误路径**打真 API 时根本复现不了**。
另用**真实 DeepSeek 端点**验证鉴权分类（真 401 → 判为致命 auth → 不降级 → CLI 退出 1）。

**验收**：42 个 Provider 层测试 + 4 个「真实 HTTP Provider 驱动完整流水线」的端到端测试；
其中一条断言「离线回放整条流水线，阶段轨迹与原始 run 完全一致」。

设计文档：`docs/08-llm-layer.md`；实现修正：`docs/07 §G`。

（`packages/server/test/server.test.ts` 用真实 HTTP + SSE 覆盖了这条路径。）

### 关键设计取舍

- **不在前端重复实现投影逻辑**：收到事件后去抖重新拉 `/api/state`。
  两套归并规则迟早会漂移，而那种 bug 表现为「界面状态与实际不符」，极难排查。
- **引擎保持零依赖**：`apps/web` 刻意不列入 workspace。
  控制台需要 React/Vite 工具链，而 `packages/*` 保持 `node xxx.ts` 开箱即用
  （见 `docs/07 §H5`）。
- **离线演示模式**：不需要任何 API key 就能把整套机制跑起来看懂。

实现修正：`docs/07 §H`（Windows 可执行解析、修复无效检测、事件未被 emit、Vite 沙箱问题、
载荷出口不一致导致的白屏）。

## P3 · 锚点靶场标定（✅ 完成）

已交付：

- 用户诉求是「多层检测锚点防止幻觉」，而在 P3 之前我们只能说「A2 能抓出幻觉符号」（因为有测试），
  说不出它的**检出率**与**误报率** —— 而防幻觉机制的价值完全由这两个数字决定
- `packages/anchors/bench/` —— 靶场骨架与 **42 个样本**（28 个注入 + **14 个干净对照组**）
- `scripts/anchor-benchmark.ts` —— 运行器，自动生成 `docs/10-anchor-benchmark.md`
- `packages/anchors/test/benchmark.test.ts` —— 把靶场锁进 `npm test`（防止锚点回归）

**结果**：

| 指标 | 值 |
|---|---|
| 样本 | 42（注入 28 + 干净对照 14） |
| 检出率 | 100% |
| **干净通过率（零误报）** | **100%** |
| 漏报 | 0 |
| 误报 | 0 |

**为什么必须有干净对照组**：只测「能不能抓出问题」毫无意义 ——
一个永远返回 FAIL 的锚点检出率是 100%。
误报与漏报**同样有害**：漏报让幻觉通过；误报把诚实代码判成幻觉，
角色被派去修一个不存在的问题（浪费轮次，还可能把对的改成错的）。
所以「干净通过率」这个数字比检出率更重要。

**靶场抓到的两个真实缺陷**（已修，见 `docs/07 §I`）：

1. **A5**：测试命令退出 0 但输出里没有任何可解析的计数 → 原本报 `PASS`。
   它其实什么都没验证到 —— 违反 `SKIPPED ≠ PASS`。已修为 `WARN(test-counts-unparsed)`。
2. **A7**：端点只写在注释里（`// TODO: 实现 /api/tasks`）→ 端点覆盖检查被字符串匹配骗过。
   已修为先剥注释再匹配。

> 首轮跑出「0 误报 0 漏报」时没有被当成好消息：
> **一次就全过通常意味着样本太贴合被测对象的强项**。主动加了对抗性样本之后才抓到这两个洞。

**报告里明确写下的局限**（`docs/10-anchor-benchmark.md`）：
样本是手写的（自出题自答）；A1 的远端核实未纳入（**当前最大的一块未覆盖区域**：
编造一个名字合法、也不像知名包的假包，本靶场抓不到）；
A4/A5/A6 用的是确定性假命令（真实工具输出的解析由 P6 覆盖）；
样本量小，召回率粒度粗；**没有测量「语义用错」这类隐蔽幻觉**（那属于 B 层，依赖 LLM）。

**未做**（原计划的其余部分，优先级低于「用真实 LLM 验证」）：

- A1 接真实 registry 并在靶场里纳入远端核实
- A2 用 TS Compiler API 的 `getExportsOfModule` 替换当前的解析降级路径
- A5 覆盖率阈值
- A7 OpenAPI / JSON Schema 响应校验（当前只做路径覆盖与重复模型检测）
- 锚点依赖排序与增量重跑

## P5 · 圆桌与人在环实战（✅ 机制完成，真实 LLM 辩论未验证）

圆桌机制全部实现并有测试覆盖，**离线 Mock 下已端到端跑通**；
尚未用真实 LLM 的多角色辩论验证过（这一点是 P5 唯一未完成项，原因见文末）。

已完成：

- 触发 T1–T5（机械判定，不可被角色否决）
- 证据核验丢弃无证据发言（引用不存在的文件/工件 → 该发言作废）
- **第 2 轮交叉质询 + 当场执行 falsifier**（`docs/05 §1.2.2`）：
  `sustained` → 记为机械事实；`refuted` → 该发言被丢弃、不进决议输入；
  `inconclusive` → 不裁决、不惩罚（执行不了 ≠ 说错了）
- 质询对象由机械决定：机械归因优先，无归因时轮转配对（避免围攻同一个人）
- **机械事实约束决议**（`docs/05 §1.2.3`）：决议不得把责任归给
  已被机械证据证明其没问题的角色；转向「需求/契约缺陷」同样被拒并升级真人
- 反和稀泥机械校验（无行动项 / 无 owner / 验收条件不可机械验证 / 否决措辞）
- 2 轮上限；无效决议 → 升级真人（第 2 层）→ 真人不可用 → 带债通过（第 3 层）
- 建议书五类型全支持 + 约束由 A1 锚点在 Gate 中真正强制校验

**新增演示场景 `cross-exam`**：唯一演示第 2 层逃生（升级真人）的场景 ——
`backend` 对 `test` 提出一个**真的会失败**的可执行反驳（检查测试是否
真的 import 了被测模块），当场执行后被确证；随后产出的决议却习惯性地
把责任推给 `pm`，与机械证据矛盾 → 判无效 → 升级真人。

尚未完成：

- **真实 LLM 多角色辩论**：需要在真实模型下才会出现真实的争议与真实的
  falsifier 提议。离线 Mock 只能验证机制本身，**不能**说明机制在真实模型下的表现。
- **升级超时策略**（超时 → 自动带债通过）：当前 run 在 `AWAIT_HUMAN` 处即终止，
  「等待期间超时」需要可恢复的 run（resume）设计，属于独立工作量，暂不做。

**验收**：构造一个必须靠圆桌解决的真实争议（如契约变更影响两角色），走完全流程。
—— 离线侧已完成（`cross-exam` 场景）；真实模型侧待做。
