# 06 · 可观测性与可复现

## 一句话

**这套系统能回答三个问题：那次调用它看到了什么、这个结论凭什么得出、同一个输入能不能跑出同样的结果。**

前面两个字"可观测"一般的多 Agent 系统都做得到（打日志）；
第三个字"**可复现**"才是关键差异 —— 因为只有可复现，"是模型不行还是编排不行"才有答案。

## 一、四层观测（从粗到细）

| 层 | 载体 | 回答的问题 |
|---|---|---|
| ① 阶段轨迹 | `decisions.jsonl`（哈希链） | 走到哪一步了？每一关的判定和动作是什么？ |
| ② 调用记录 | `runs/run-*.jsonl` | 每次调用的 purpose / 温度 / schema / token / 耗时 / **上下文注入情况** |
| ③ 工件与锚点链 | `artifacts/` | 每个工件的内容哈希、锚点结论、被谁否决 |
| ④ 契约基准 | `project.contract.snapshot` | 验证基准是什么？产出有没有试图篡改它？ |

## 二、决策日志：哈希链 + 严格落盘顺序

每条决策记录都带 `prev` 哈希，形成链 —— **任何一条被改过，链就断了**。

这里踩过一个非常隐蔽的坑 `[实测]`：**并发 `append` 会让 seq 16 先于 15 落盘**，
于是哈希链校验偶发失败（3 次运行挂 1 次）。不是逻辑错，是写入顺序错。
修法是给 `append` 加一条**串行写入链**，保证**磁盘顺序 === seq 顺序**。

> 这个 bug 的价值在于它示范了一件事：**可观测性本身的正确性也需要被验证**。
> 一条"偶尔断"的哈希链，会让人误判成"有人篡改了日志"。

## 三、输入审计：这一轮新增的能力（也是本项目最大的教训）

**问题**：所有观测都只在看**产出**。没有任何地方记录"角色到底看到了什么"。
于是当 30 次调用的输入 token 恒定在 10.6k、而项目从 0 行长到 4,443 行时，
**系统里没有任何一处能回答"为什么"** —— 只能事后用盘上的工件复算，花了两小时。

**现在**：每次调用的记录里带一个 `context` 字段：

```json
{
  "seq": 6, "role": "backend", "purpose": "produce:CodeModule:api",
  "context": {
    "budget": 60000,
    "used": 23507,
    "injected": [
      { "id": "Requirement-001", "kind": "Requirement", "chars": 5677 },
      { "id": "PRD-001", "kind": "PRD", "chars": 5413 },
      { "id": "Contract-001", "kind": "Contract", "chars": 2897, "digest": true },
      { "id": "CodeModule-T-003", "kind": "CodeModule", "chars": 9520, "card": true }
    ],
    "omitted": [
      { "id": "TaskGraph-001", "kind": "TaskGraph", "chars": 15520, "reason": "tier-cap" },
      { "id": "TestSuite-001", "kind": "TestSuite", "chars": 51151, "reason": "no-space" }
    ]
  }
}
```

三个设计要点：

1. **只记 id + 字符数，不记正文** —— 不增加存储负担，也不把敏感内容写进日志
2. **`reason` 区分 `tier-cap` 与 `no-space`** —— 前者要调分层比例，后者要加预算，**修法不同**
3. **`digest` / `card` 标记** —— 让"看到的是摘要/接口"和"看到的是全文"可以区分，
   否则又会变成"看起来注入了，其实只是骨架"

配套的 `scripts/run-progress.ts` 直接把这一行印出来：

```
上下文：23,177 / 60,000 字符（39%）  注入 3 个·丢弃 0 个  [pm · produce:Contract]
  其中接口卡 0 个、契约摘要 1 个
  未注入：TaskGraph-001(15520·tier-cap) …
```

> **"模型是不是被饿着在写"应该一眼可见，而不是靠复算。**

## 四、回放：同一输入能否跑出同样结果

`RecordingProvider` 把每次调用（含 prompt 哈希）落盘；`ReplayProvider` 用记录回放。
回放键 = `purpose + promptHash + attempt`。

**用途**：
- 改编排逻辑时，用同一批模型输出回放，**区分"是我的改动导致的失败"还是"模型这次输出不同"**
- 模型输出是温度 0.1 下的采样，本来就不确定 —— 回放把不确定性从实验里摘出去

**已知限制**（诚实说明）：回放只能重放**模型输出**，不能重放**文件系统状态**。
如果锚点依赖盘上文件（A4/A5 必然依赖），回放时环境必须一致。

## 五、锚点靶场：用 45 个样本标定"检查本身准不准"

这是可复现性的核心机制，也是最容易被忽略的一环。

**问题**：怎么知道一条锚点"抓得准"？没有标定的话，锚点就只是"作者觉得它有用"。

**做法**：45 个样本（30 个注入缺陷 + 15 个干净对照），每个都精确构造：

| 结果 | 含义 |
|---|---|
| TP | 注入了缺陷、且被抓到 |
| FN | 注入了缺陷、没抓到（**最危险**） |
| FP | 干净代码被误报（**第二危险**，会毁掉锚点信誉） |
| TN | 干净代码正确放行 |
| **严重度不符** | 抓到了但比期望更重（说明期望过期，不是能力退化） |

当前基准（`[实测]`）：**TP 30 / FN 0 / FP 0 / TN 15 / 严重度不符 0**。

**两个反直觉的经验**：

1. **"干净通过率"比"检出率"更重要。** 一条会对好代码报警的检查，
   会让角色学会"这条可以糊弄过去"，此后它所有的真报都会被降权。
   我们为此专门验了"新增的两条可达性检查在自研代码库 93 文件 / 190 个导出上零误报"。
2. **改了严重度必须重跑靶场。** 我们把两条检查从 WARN 提到 FAIL 后没跑靶场，
   于是样本里的期望还是 WARN，指标显示"TP 28 → 26、严重度不符 2"，
   看起来像检出能力退化，实际是**期望过期**。直到有人顺手跑了一次靶场才暴露。

## 六、Web 控制台

`packages/server` 提供只读 API，React 控制台展示：
阶段轨迹、锚点状态、工单、圆桌纪要、成本、工件树。

**设计立场**：控制台**只读**。它不能用来"手动放行"——放行必须走真人建议书（`Directive`），
那条路径有审计、有类型（`override` / `resume` / `let-it-pass`）、也有次数限制。
**能改变系统行为的操作必须留下同名可查的记录。**

## 七、答辩可能被问到

**Q：可观测性听起来像运维话题，和 AI 有什么关系？**
A：因为多 Agent 系统的失败**长得像能力问题**。没有输入审计，你会花两周去换模型、
调提示词，而真正的原因是"契约没进上下文"。
**可观测性在这里不是运维，是归因的前提** —— 没有它，所有优化都是猜。

**Q：哈希链能防谁？**
A：防不了有权限改全部文件的人。它防的是**无声篡改**：
如果一段日志被改过，后面所有记录的 `prev` 都对不上，一眼可见。
这在比赛/评审场景里意味着"这些结论不是事后编的"。

**Q：45 个样本够吗？**
A：不够，但方向对。45 个样本能覆盖 11 条锚点的主要失败模式，
不足以给出统计意义上的召回率。我们更看重的是**零误报**这个性质 ——
样本少时宁可保守，也不要为了刷分往里面塞容易过的样本。
