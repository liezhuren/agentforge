# 01 · 场景价值

## 一句话

**把"AI 说它做完了"变成"机械证明它能跑"—— 这是 AI 编程从"演示"走向"交付"的必由之路。**

## 一、真实痛点：AI 编程的失败是"假绿灯"式的

现在的 AI 编程工具（Copilot / Cursor / Devin 类）最大的问题不是"写不出代码"，
而是**写出来的东西看起来完整、实际跑不起来，而工具自己不知道**。

这不是猜测，是我们自己跑出来的 `[实测]`：

一次真实的"生成一个茶歇系统"运行，产出如下：

| 表面指标 | 值 | 看起来 |
|---|---|---|
| 代码量 | 18 个模块 / 4,443 行 | 挺完整 |
| 类型检查 | `tsc --noEmit` **通过** | 没毛病 |
| 契约端点 | 17 个端点，**代码里全都出现过** | 都实现了 |
| 测试 | 写了 39 条测试 | 有质量意识 |

然后真的去跑：**39 条里 28 条失败，全部是 HTTP 501。**

原因是一行代码：

```ts
if (isProtectedRoute(method, pathname)) {
  const user = currentUser(req);
  if (user === null) { sendJson(res, 401, ...); return; }
  sendJson(res, 501, { error: 'not implemented yet', path: pathname });  // ← 直接占位
  return;                                                                //   从不调用业务模块
}
```

而 `papers.ts` / `comments.ts` / `friends.ts` / `interests.ts` 全都导出了 `handleXxx()`，
**整个项目没有一处调用它们**。

**AI 工具在这一刻会说"已完成"。人类工程师打开测试才知道真相。**
两小时的调试，换来一句"它其实没做"。

## 二、为什么这不是"模型不够强"

我们最初也这么以为，直到把数据拆开 `[实测]`：

| 观察 | 表面解释 | 真实原因 |
|---|---|---|
| 端点路径都对，但全是 501 | 模型偷懒 | **它不得不偷懒**：契约（60,720 字符）根本没进它的上下文 |
| 模块之间不互相调用 | 模型不会架构 | **它看不见别人**：11 个代码模块一件都没进上下文 |
| 连修 6 轮不收敛 | 模型能力不足 | **它在盲修**：测试报告（2.5k 字符，6 轮）一次都没进上下文 |

复算结果：24,000 字符的上下文预算，被"需求 + PRD + 任务图"三件散文吃掉 **95%**，
剩下 1,176 字符 —— 契约、代码、测试报告**一件都塞不进去**。
54 万字符的工件里，真正送达模型的只有 **4.2%**。

> **结论：多 Agent 系统的失败往往不是能力问题，而是编排问题。**
> 而编排问题不会自己报错 —— 它只会让模型"看起来很笨"。

这就是 AgentForge 存在的理由：**编排需要被当作一等公民来验证**。

## 三、目标用户与场景

| 用户 | 痛点 | AgentForge 给什么 |
|---|---|---|
| **AI 编程工具的开发者** | "我的 Agent 成功率上不去，但不知道卡在哪" | 一套可复用的**验收骨架**：11 条确定性锚点 + 机械归因 + 靶场标定方法 |
| **要交付 AI 生成代码的团队** | 不敢把 AI 产物直接上线，人工 review 成本高 | **可审计的交付结论**：每个工件绑定内容哈希，每条结论可复现、可回放 |
| **多 Agent 系统研究者** | 系统出错时无法区分"模型问题"和"编排问题" | **决策日志哈希链 + 输入审计**：能回答"那次调用它到底看到了什么" |
| **参加类似竞赛/课程项目的学生** | 想用 AI 快速做出能演示的系统 | 一套确定性的"最后一公里"检查，避免演示当天 501 |

## 四、差异化：为什么不是"又一个 Agent 框架"

大多数 Agent 框架解决的是**"怎么让 Agent 干活"**（工具调用、记忆、规划、协作协议）。
AgentForge 解决的是另一个问题：**"怎么判断 Agent 干完了没有，以及没干完时怪谁"**。

三条机制上的差异：

### 1. LLM 永远不是最终裁判

- 结论必须来自可复现的机械检查（编译、执行测试、解析导入、比对哈希、运行时探针）
- 语义判断（"这条需求达成了吗"）也是 **LLM 提议 + 机械核验证据**：
  证据必须指向**真实存在的文件**和**真实的行号区间**，且那段内容必须真的支持结论。
  编造的证据会让整条判定作废（`INVALID_EVIDENCE`），不是"扣分"。
- 不变式：**`SKIPPED ≠ PASS`**。命令没配、环境跑不了时，锚点报 `SKIPPED`，
  绝不偷偷算作通过 —— 我们为此专门写了测试守着。

### 2. 失败必须被机械归因

每条锚点失败都带 `targetRole`，直接生成派工单，**不需要再让 LLM 猜"这该怪谁"**。
这不是省 token，而是避免"归因错 → 改错地方 → 越改越差"。

实测的归因粒度差异：同样的失败，`A4`（编译错误）能精确到**文件 + 行号**；
`A7`（契约漂移）能精确到**哪个端点、哪个模型**；`A1`（依赖）能精确到**哪个包名**。

### 3. 有界阻断：主理人不能把项目卡死

主理人（host）能提异议、能阻断 —— 但在同一阶段**阻断 3 次后阻断权自动终止**，
强制转圆桌会议。这是"双 Agent 互审"类设计里最容易失控的地方：
两个 Agent 互相否决，系统永远不前进。我们用一条账本规则把它变成**有界的**。

## 六、演示时会说的那句话

> "各位看到这个网页能登录、能发论文、能评论。它不是人写的 —— 是 5 个 AI 角色协作产出的。
> 而比这更重要的是：**如果它其实没做对，这个系统会自己说出来，并且告诉我是哪个 AI 的错。**
> 我们三轮真实运行里，它抓出了 12 个"写了但没接线"的端点、28 条假通过的测试。
> 这才是让 AI 编程能真正交付的东西。"
