# 04 · 异常处理与自愈

## 一句话

**四层逃生，全部机械判定，且保证一定有出口 —— 这套系统不会因为"几个 AI 谈不拢"就卡死。**

## 一、失败分四类，处理方式完全不同

| 类别 | 例子 | 谁来判 | 处理 |
|---|---|---|---|
| **产出格式错** | 模型返回的不是合法 JSON / 不满足 schema | `validateSchema` | 把**具体校验错误**回喂重试（不是盲目重试三次） |
| **可机械归因的失败** | 编译错、测试挂、依赖没声明、端点没实现 | A 层锚点 | 定位到文件/行号/端点 → 生成工单 → 打回那个角色 |
| **需要协商的争议** | 两个角色产出矛盾、归因完全失灵 | 圆桌 T1–T5 | 两轮辩论 → 决议必须过 schema → 行动项绑定角色 |
| **无法归因且真人不可用** | 圆桌也谈不拢 | `decideEscape` | **带债通过**：记账 + 需求标 `accepted_with_debt`，继续推进 |

## 二、四层逃生阶梯（这是"不会死锁"的最终保证）

```
① 打回返工（RETRY_ROLE）—— 便宜、确定、有明确验收条件
      ↓ 同一阶段阻断 3 次 / 归因完全失灵
② 圆桌会议（ROUNDTABLE）—— 唯一允许 LLM 协商的地方
      ↓ 圆桌未产出有效决议
③ 升级真人（ARBITRATE_HUMAN）—— 打包成仲裁包，人只需做一次决定
      ↓ 真人不可用（离线 / 超时）
④ 带债通过（PASS_WITH_DEBT）—— 显式记账，不掩盖
```

`decideEscape()` 是**纯函数**，三个分支穷举了所有情况，所以它**一定返回一个可执行动作**：

```ts
export function decideEscape(args): EscapeDecision {
  if (!args.roundtableAttempted) return { layer: 1, action: 'ROUNDTABLE', ... };
  if (args.lastResolutionValid === true) return { layer: 1, action: 'ROUNDTABLE', ... };
  if (args.humanAvailable) return { layer: 2, action: 'ESCALATE_HUMAN', ... };
  return { layer: 3, action: 'PASS_WITH_DEBT', ... };  // ← 永远有出口
}
```

> 这是不变式"**主理人无法让项目停死**"的代码形态。
> 没有这个函数，两个 Agent 互相否决就能让系统永久停在某个阶段。

## 三、四条"防空转"的具体机制（每一条都是被真实失败逼出来的）

### 机制 1：阻断权有界（`stageBlockLimit = 3`）

主理人（host）能提异议、能阻断，但同一阶段**第 3 次阻断后权限自动终止**，强制转圆桌。

**为什么**：双 Agent 互审类设计最容易失控的地方就是"互相否决"。没有上限时，
host 可以无限次说"我不同意"，系统永远不前进。

### 机制 2：能归因就先打回，一条都归不了因才开会

判定条件从 `roles.length >= 2` 一路收紧到 `roles.length === 0`。

**为什么**（实测教训）：第一版只要归因分散到多个角色就把整个阶段拖进圆桌，
于是"A6 明明已经明确归到 backend、本可以直接打回返工"也会陪着开会。
12 轮真实运行里开了 **15 场圆桌，绝大多数毫无必要**。
**甩锅不需要开会解决 —— 派工单天然支持一次派给多个角色。**

### 机制 3：不为"没变化的失败"反复开会

规则：已经开过圆桌、且本轮硬失败签名与上一轮**完全相同** ⇒ 不再开会，改为打回，
由编排层识别"修复无效"并转逃生流程。

**为什么**（实测）：出现过某阶段连开 **6 次** T4 圆桌 ——
开会 → 派工单 → 返工 → 签名**完全没变** → 又满足触发条件 → 再开会 …… 纯烧钱。

### 机制 4：修复无效 ⇒ 直接带债通过，不再重试

实测日志（cb-3 的真实输出）：

```
[CONTRACTING] 工单修复后硬失败签名未变（pm 的修复没有改变任何东西），
              不再重复重试，转逃生流程
带债通过：派给「pm」的 1 张工单执行后，锚点失败情况与修复前完全一致。
          继续重试同一个角色不会有效果 —— 可能是该问题不属于角色的职责范围
          （例如工具链配置本身有误）（受影响需求 3 条，已标记 ACCEPTED_WITH_DEBT）
```

**这段日志的价值**：它不但承认失败，还给出了**最可能的错误假设**——
"这个修复可能不属于该角色的职责范围"。这就是可归因系统该有的样子。

## 四、上下文超长：自适应而不是崩掉

模型报"上下文超长"时，`runWithRetry` 会自动**预算减半重试**，
且**不消耗产出重试次数**（那是同一轮，只是换了更小的上下文）。

```ts
if (CONTEXT_OVERFLOW_RE.test(msg) && contextBudget >= MIN_CONTEXT_CHARS * 2) {
  contextBudget = Math.floor(contextBudget / 2);
  attempt--;        // 不算一次产出失败
  continue;
}
throw e;            // 认证错误等照旧抛出，不许被当成"预算问题"吞掉
```

**为什么要有这条**：一次 400（context too long）原本会让整轮 run 终止 ——
最不划算的失败方式（已经烧掉的 token 全白烧）。
同时**不能把什么错误都当成预算问题**：401 说明密钥错了，减半重试毫无意义。

## 五、锚点自身出错也不许拖垮 Gate

锚点抛异常时，Gate 会把它转成 `FAIL` 并记录原因，**不是让整个进程崩掉**。
有专门测试守着这一条。

同理 `A6`（运行时探针）：服务起不来必须转成**一次报告**，绝不能让整个进程崩溃。
（Windows 上还踩过"必须把 npm 解析成 npm.cmd"的坑 —— 否则探针永远跑不起来，
看起来像"服务没起"，实际是命令解析问题。）

## 六、`SKIPPED ≠ PASS`：最容易被忽略的一条

如果命令没配（没有 `typecheck` 脚本）、环境跑不了（离线、缺依赖），
锚点报 **`SKIPPED`**，并且在结论里明说"未验证 ≠ 通过"。

**为什么这条重要**：所有人都倾向于把"没检查"和"检查通过"混为一谈，
因为前者看起来像"没问题"。我们的靶场里有专门的对照组守着：
**干净通过率**（对照组里无任何硬失败的比例）比检出率更重要 ——
如果一条检查会对干净代码误报，它就会被角色学会"糊弄过去"，此后所有真报都会被降权。

## 七、答辩可能被问到

**Q：带债通过不就是"糊弄过关"吗？**
A：它和"糊弄"的区别是**可查**。带债通过会写 `DebtRecord` 工件、
把受影响需求标成 `accepted_with_debt`、生成 `TECH_DEBT.md`，
并且交付结论里两条轴分开显示（`delivery` 能不能跑 vs `requirementStatuses` 达没达成）。
**我们不能假装成功，但也不允许系统卡死 —— 所以选择"明确记账后前进"。**

**Q：万一 `decideEscape` 的判断本身错了呢？**
A：它是纯函数，输入是四个布尔/计数，能单测覆盖全部分支。
而且它的错法只有两种：早一轮开会（浪费一点钱）或早一轮带债（少修一个 bug）。
我们选了"早失败"方向 —— 因为**卡死比带债更糟**。

**Q：三次阻断上限为什么是 3？**
A：这是我们唯一**没有标定**的参数（诚实说明）。理论上应该按"平均几次返工能收敛"来定，
而我们目前的样本量还不足以给出这个数。它现在是一个保守的经验值。
