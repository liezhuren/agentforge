不要用感觉判断。本次改动的验收标准只有三条，按重要性排序：

## 二、[已观察] 四轮在 CONTRACTING 就分叉了

这是本次运行最重要的早期信号，**必须先解释清楚**：

| 工作区 | CONTRACTING 结果 | A7 失败内容 |
|---|---|---|
| cb-5 | **seq1 一次通过**（A7:WARN） | — |
| cb-6 | **seq1 一次通过**（A7:WARN） | — |
| cb-7 | 连挂 2 轮 → **带债通过** | `phantom-contract-path` **×15** |
| cb-8 | 连挂 2 轮 → **带债通过** | `orphan-contract-path` ×1、`orphan-contract-schema` |

**结论：CONTRACTING 的"切片覆盖"检查是当前第一卡点，命中率 2/4。**

诊断细节（都是实测，不是推测）：

### cb-8：唯一的孤儿端点是 `/api/{any}`（catch-all）

```
契约 15 个真端点；TaskGraph 10 个任务；未被认领: ["/api/{any}"]
```
这是**误报的性质**：catch-all 路由本来就不该有独立实现任务。但它仍然应该被某个任务"认领"
（比如 T-008 那个 `contractPaths: []` 的错误处理任务），所以**检查没有错，是工单没说清楚**。

### cb-7：契约里只有 **1 个端点**（`/health`），任务图却声明了 15 个

```
契约 14,153 字符，openapi.keys = [openapi, paths, components]
paths 只有 /health
jsonSchemas 有 20 个（很完整！）
未被认领: []     认领了但契约没有: 15 个
```
所以 `phantom-contract-path × 15` 是**完全正确的报警** —— 任务图在引用一个不存在的接口。
根因是 **PM 生成契约时只枚举了 1 个端点，却把 20 个模型写得很完整**。
不是截断（`paths` 在 `components` 之前，截断会切掉 components 而不是 paths）。

### 已采取的修复（在本轮 4 个 run **之后**才生效）

`acceptanceFor()` 里 `orphan-contract-path` / `phantom-contract-path` / `*schema` /
`contract-non-operation-path` 原来全部落到 `default` 分支，PM 收到的工单是：

> 「修复 项目 的 orphan-contract-path 问题，使 A7 锚点 PASS」

**一句不可执行的话。** 这就是 PM 连修两轮"没有改变任何东西"的直接原因。
现在每个 code 都有具体指令（点名端点、点名 contractPaths），并新增 3 条测试守着
"不许再落到 default"。

> **教训**：凡是有专门 `code` 的失败，就必须有**专门的验收条件**。
> 落到 `default` 等于默认"修不好也能凑合"，而且那句话本身在告诉模型"我也不知道该改什么"。

## 三、失败模式清单（按"最可能先遇到"排序）

### F1 · CONTRACTING 反复卡住 → 带债进入 BUILDING

**判据**：`run-progress` 里 CONTRACTING 出现 `✗1` `✗2`，随后工件里出现 `DebtRecord`。

**为什么致命**：契约是整条链路的地基。带债进入 BUILDING 意味着
**3 条需求在写第一行代码前就被标成 `accepted_with_debt`** —— 最终交付里它们注定不达标。

**验证**：
```bash
node workspace/_scratch/diag-contracting.ts workspace/cb-N
```
看三件事：契约真端点数量、任务声明数量、`orphan`/`phantom` 各多少。

**判别**：
| 现象 | 原因 | 修法 |
|---|---|---|
| `phantom` 很多、契约端点极少（如 cb-7） | **PM 契约生成质量差** | 加一条"契约端点规模"检查 + 在 PM 提示词里要求逐条需求枚举端点 |
| `orphan` 只有 1–2 个、且含 `{any}` 这类通配 | 检查过严 | 把纯通配路径排除出"必须认领"（或允许 catch-all 任务认领） |
| `orphan` 很多 | PM 切片覆盖不全 | 已修：工单现在会点名端点 |

**优先级**：**最高**。它决定了这一轮是不是从地基就坏了。

### F2 · BUILDING 第一轮就报出大量 `unwired-handler`

**判据**：`A7` 失败里出现 `unwired-handler`，且数量 ≥ 3。

**两种完全相反的解读，必须分清**：

- ⚠️ **坏消息**：说明模型**仍然没有接线**，接口卡没解决根本问题

**怎么区分**：看它是否在同一轮内被修好。

- 连续 3 轮数量不变 → 坏消息（→ 见 F3）

### F3 · 连续多轮 `unwired-handler` 数量不变（不收敛）

**这是本轮实验最坏的结果**，意味着"信息饥饿"不是充分原因。

**验证顺序**：
1. **先确认契约和接口卡真的送到了**：
   ```bash
   node scripts/run-progress.ts workspace/cb-N
   # 看 "上下文：X / 60000（Y%） 注入 N 个·丢弃 M 个" 和 "其中接口卡 K 个"
   ```
   如果 `接口卡 0 个` 或 `丢弃` 很多 → 是**上下文还没修好**，回到 F8。
   如果接口卡在、契约在（摘要）、测试报告在 → 进入第 2 步。
2. **确认工单措辞被读到了**：看 run log 里 repair 调用的 prompt 是否包含
   "加 export 别名不算接线"。
3. **如果两者都满足仍然不收敛** → 结论是**模型能力/指令不足**，需要：

| 修法 | 代价 | 预期 |
|---|---|---|
| 在 `codeInstruction()` 里加"新增模块必须从入口可达；只写模块不接线 = 没完成" | 小 | 事前告知比事后返工便宜 |
| 任务图要求一个显式的"集成"任务 | 中 | 让"接线"有主 |
| 给 app 分发逻辑一个**骨架模板**（确定性生成，不让 LLM 发明） | 中 | 直接把"接线"从生成问题变成填空题 |

> 第三条其实是性价比最高的：**分发逻辑是可以被确定性生成的**（路由表 + 契约端点 + 模块导出签名
> 三者都在，组合方式是机械的）。不让 LLM 写这一段，就消掉了这个失败模式。

### F4 · A5 仍然大面积失败（28 → 20+）

**判据**：REVIEW/BUILDING 的 A5 报 `fail` 数 ≥ 15。

**先看失败内容**，它决定原因（**不要看数量，看第一条错误**）：

| 失败内容 | 原因 | 修法 |
|---|---|---|
| `expected 201, got 501` | 仍是占位/未接线 | 回到 F2/F3 |
| `ECONNREFUSED` | 服务没起来（自启没写对） | 见 F6；检查 `src/index.ts` 或 `server.ts` 是否真的 `listen` |
| `Cannot find module '../../shared/contract/types.ts'` | 导入路径/扩展名错 | 环境约定没传达；`environmentNotes` 已声明"必须带 .ts" |
| `expected 200, got 404` | 路径不匹配（契约 vs 实现） | A7 `undeclared-endpoint` 应该同时报；若没报则是契约本身错 |
| 断言值不对（如排序、字段名） | 语义实现错 | 正常返工；看工单是否给了具体验收条件 |

**关键判断**：如果失败里 **501 比例低于 30%**，说明接线问题基本解决，
剩下的是普通实现 bug —— 那是**好消息**（L2 达标），只是还需要更多轮次打磨。

### F5 · A4 编译错误反复出现

**判据**：A4 连续 2 轮 `compile-error`。

**先看错误类型**：
- `TS2835: 相对导入路径需要显式扩展名` → 环境约定没被遵守（已知问题，`environmentNotes` 里写了）
- `TS2339: 属性不存在` → 模型自己写的类型不一致（正常返工）
- `Cannot find name 'process'` / 缺 `@types/node` → 工具链问题，不是模型问题

**注意**：如果是工具链问题，它会被错误归因到角色头上。
用 `docs/07 §L6` 那条经验：**先区分"环境问题"和"代码问题"**，
否则会一直派工单给一个改不了它的角色。

### F6 · A6 运行时探针失败

**判据**：A6 `FAIL`（`runtime-probe-failed`）或 `SKIPPED`。

**四种可能，按概率**：
1. **入口没有自启**（`src/index.ts` 只导出函数，没 `listen`）→ 最常见，工单要写"入口文件被直接执行时必须自己监听"
2. **端口冲突**：4 个 run 并行时如果端口配错，A6 会探到别人的服务（**假绿灯**）或连不上
   ```bash
   Get-NetTCPConnection -State Listen | Where-Object { $_.LocalPort -in 8787,8788,8789,8790 }
   ```
   每个工作区的 `package.json` 里 `agentforge.healthUrl` 必须是**自己的端口**
3. **启动超时**：服务起来了但依赖加载慢
4. **健康检查路径不对**：契约写 `/health`，实现写 `/api/health`

**注意**：A6 是唯一能证明"这东西真的能跑起来"的锚点。它 SKIPPED 就等于没验证。

**判据**：日志出现"工单修复后硬失败签名未变……转逃生流程"。

这**不是 bug**，是设计（机制 4）。但要判断是哪种情况：

| 真的改不动 | 模型能力边界 | 转人工补完（见 §七） |

### F8 · 上下文仍然不够（60k 是否够）

**判据**：`run-progress` 的上下文行出现 `丢弃` 很多，或 `used / budget` 长期贴着 100%。

**注意看 `reason`**：
- `tier-cap`（该层额度用完）→ 调分层比例，**不是加总预算**
- `no-space`（总预算不够）→ 才是加预算

**当前分层**（backend）：规格 15% / 执行事实 10% / 模块接口 25% / 代码全文 25% / 需求计划 25%。

**如果 `TestReport` 被丢** → 严重，说明执行事实层不够，要提它的 share。
**如果 `Contract` 是 digest 且模型仍写错接口** → 摘要信息不足，要提规格层 share
（摘要只保留端点/方法/状态码/字段类型，丢了必填/枚举/边界约束）。

### F9 · 模型误解了接口卡

**判据**：产出里出现"我以为这个文件已经有实现了"这类表述，或重复实现别人模块的功能。

**验证**：看 repair 的 prompt，接口卡的格式是：
```
--- 接口 CodeModule-T-003（CodeModule/api by backend v1）---
@@@ 模块 CodeModule-T-003 v1
@@ src/api/papers.ts
export function handlePapersRoute(request: PapersRequest): PapersResponse | null
```

**风险点**：模型可能以为"接口存在 = 实现存在"，于是不去调用。

**修法**（低代价）：在渲染接口卡时加一行明确说明：
> 「以上是**其他模块导出的签名**（不是完整代码）。它们由别的任务实现；
> 你需要在**自己的模块里 import 并调用**它们，不要重复实现。」

**这条如果没做，很可能是 F3 的隐藏原因。**

---

### F10 · 输出仍然爆炸（重写税没降）

**判据**：输出/输入 > 1.5，或单次 `repair` 输出 > 3 万 token。

对比基线（cb-2）：输出/输入 = 2.2，72% 输出花在重写。

**如果没降**，说明"能看见上一版"这件事还没生效。检查：`repair` 时该工件的当前版本
是否在上下文里（`injected` 里应该有那个 `CodeModule` 的**全文**，不只是接口卡）。

**修法**：
- 短期：`repair` 请求显式带上"被修工件"的当前全文（按 artifact id 强制注入，占配额）
- 长期：改成增量 patch 输出（需要新 schema + 合并逻辑）

> 修法应转向 F3 的三条（尤其"确定性生成分发逻辑"）。

## 九、如果评委问「为什么成功率低」—— 标准答法

> 这是**最可能被问到、也最容易被答坏**的一题。
> 答坏的方式有两种：否认（"其实是环境问题"）或认输（"模型还不够强"）。
> 正确的答法是**先把口径改对，再说明低是这个系统的输出而不是它的缺陷**。

### 9.1 一句话版（先背下来）

> **"我们统计的不是'AI 能不能写出代码'，而是'AI 写出的代码能不能被证明是对的'。
> 这两个数字本来就该差很多 —— 差多少，正好就是这套检查的价值。"**

### 9.2 三层递进（按这个顺序讲，不要跳）

**第一层：先修分母（10 秒）**

> "先说口径。我们一共跑了 25 次，其中 12 次是进程被环境回收、没跑完 5 个门禁 ——
> 那 12 次不构成判定，不算失败。公平口径是 13 次真实运行：
> **2 次完整交付、4 次带债收场、7 次中途被杀**。"

**第二层：低成功率是这个系统的**输出**，不是它的 bug（20 秒）**

> "如果一套'AI 研发系统'的成功率是 100%，那它的验收一定是假的 ——
> 因为验收的全部工作就是**拒绝**那些不该交付的东西。
> 我们有一条实测反例：模型写出 4,443 行、tsc 通过、39 条测试，
> 但 12 个端点一律返回 501 —— 而普通工具会报『已完成』。
> **在没有检查的世界里，成功率是 100%，但那是假的。**"

**第三层：失败集中在一类可命名的问题上，不是"处处都不行"（30 秒）**

> "203 次硬失败里，63% 集中在两条锚点：A7（任务图与契约漂移）和 B2（需求没进 PRD / 没被任务实现）。
> 而单工件类的失败 —— 编译错、测试挂、服务起不来 —— **基本一轮就修好了**。
> 所以准确说法是：**它不是普遍不行，是有一类问题不行：跨工件的一致性。**
> 这一类我们已经有明确修法：让契约从任务图单向派生、生成后先自检再提交、工单改增量。"

### 9.3 数字表（评委要看数据就念这张）

| 口径 | 数值 |
|---|---|
| 总运行 | 25 次 |
| 其中"早死"（<5 门禁，进程被杀，不计判定） | 12 次 |
| **公平口径（跑够轮次的有效运行）** | **13 次** |
| ├ 完整交付（`fullyVerified=true`） | **2 次**（14/14 需求、22/22 需求） |
| ├ 带债收场（显式记账，不冒充通过） | 4 次 |
| └ 中途被杀 | 7 次 |
| 硬失败分布 | A7 58 次 · B2 38 次 · A5 32 次 · B1 21 · B3 20 · A4/A6 各 13 |
| 最长连续失败 | A7 9 轮 · B2 8 轮 · A5 7 轮 |

### 9.4 三个必被追问的问题 + 答法

**Q1「是不是模型能力不够？」**
> "不是主因。同一批里 **A4 编译、A5 测试、A6 运行时探针都能过** —— 那是真跑 tsc、
> 真跑 30 条测试、真起服务探 HTTP。卡住的是'四份文档互相对不上'这种一致性问题，
> 它属于**工程约束**，不是模型智力。"
> （证据：brief-s2 / brief-s3 都过了 A4+A5+A6 并完整交付。）

**Q2「那你凭什么说它能交付？」**
> "因为它交付过两次，而且凭证是可复核的：`verdict.txt` 是服务端唯一判定脚本的输出，
> `gates.txt` 是 7 个门禁的锚点轨迹，`decisions.jsonl` 是哈希链日志。
> 评委可以现场跑 `scripts/show-verdict.ts` 复算。
> **更关键的是：同一套判据还拦下过东西**（一次空交付、若干次带债）——
> 一个只会放行的检查，没有资格叫验收。"

**Q3「能不能现场跑一次成功的？」**
> "能。预置场景 `real-app` 约 60 秒：真 tsc、真测试、真探针，
> 出来就是 `DELIVERED + fullyVerified`。
> 但它跑的是脚本化模型 —— 所以我会同时说明：**那一页证明的是结账链路，
> 不是模型能力**；模型能力的证据是 `brief-s2/s3` 那两次，凭证在 evidence 目录。"

### 9.5 千万别说这三句

| ✗ 不要说 | 为什么 |
|---|---|
| "主要是环境不稳定/进程被杀" | 听起来像找借口。环境问题只能放在"修分母"里一句带过，不能当主因 |
| "模型还不够强，再等等就好了" | 把项目价值让出去了 —— 而你做的恰恰是"不依赖模型变强"的验收 |
| "成功率其实还可以" | 不要争数字。要争的是**这个数字意味着什么** |

### 9.6 建议：做一页 backup（第 10 页）

标题：**「低成功率意味着什么」**，只放三样东西：
1. 公平口径那张表（13 次 → 2 / 4 / 7）
2. 硬失败分布条形（A7 58 · B2 38 · A5 32 …）
3. 一行结论：**"我们把'没做完'判成了没做完 —— 这就是它和 Demo 的区别。"**

被问到就翻这一页，不要靠记忆报数字。
