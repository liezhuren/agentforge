## 二、生成过程的锚点轨迹（这是"它会自己检查"的证据）

`workspace/cb-6` 的完整 Gate 记录（`docs/competition/evidence/cb-6-gates.txt`）：

```
INTAKE       seq1    -> ADVANCE
PLANNING     seq1  B2:WARN  -> ADVANCE
CONTRACTING  seq1  A7:WARN B2:WARN  -> ADVANCE
BUILDING     seq1  A1:WARN A2:PASS A3:PASS A4:PASS A5:PASS A7:FAIL A8:PASS B2:FAIL  -> RETRY_ROLE (ANCHOR_HARD_FAIL)
BUILDING     seq2  A1:WARN A2:PASS A3:PASS A4:PASS A5:PASS A7:WARN A8:PASS B2:PASS  -> ADVANCE
REVIEW       seq1  A1:WARN A2:PASS A3:PASS A4:PASS A5:PASS A6:FAIL A7:WARN A8:PASS B1:SKIPPED B2:PASS B3:SKIPPED  -> RETRY_ROLE (ANCHOR_HARD_FAIL)
```

**怎么读这张表（这是最有说服力的部分）**：

1. **BUILDING seq1 就有 `A5:PASS`** —— 测试**真的被执行并通过了**，
   不是"写了测试文件就算完成"。
2. 同一轮 `A7:FAIL` + `B2:FAIL` → **打回 backend 返工**（`RETRY_ROLE`），
   不是放过去。seq2 时 A7 降到 WARN、B2 转 PASS → 才 ADVANCE。
3. REVIEW 时 `A6:FAIL`：探针报"服务进程在就绪前退出（exit 1）"，
   因为那一刻 `src/api/server.ts` **还没写出来**（脚本 `start` 指向它）。
   **这是锚点抓到了一个真实的瞬时缺口**，不是误报。
4. 修复后 A6 **PASS**（`readyMs 624`，stdout 有 `[coffeebreak] listening on http://127.0.0.1:8788`）。
5. 之后进程被运行环境回收，没走到 DELIVERED —— **产品是好的，只是编排没来得及结账**。

> `B1:SKIPPED / B3:SKIPPED` 是如实标注：语义判定与主理人异议环节没跑完。
> **`SKIPPED ≠ PASS`** 是本项目的硬规矩，所以它显示为 SKIPPED 而不是 PASS。

## 三、四轮并行实验的对照（用来讲"方差"）

同一份 brief、同一版引擎、四个独立工作区（端口 8787–8790）：

| 工作区 | CONTRACTING | BUILDING | 结局 |
|---|---|---|---|
| cb-5 | ①次通过（A7:WARN） | seq1 RETRY（A5/A7/B2 失败） | 进程被回收（14 次调用 / 476k token） |
| **cb-6** | ①次通过 | **seq2 ADVANCE（A5:PASS）** | **REVIEW A6 修复后 PASS；产物可运行 22/22 + 33/33** |
| cb-7 | ✗2 次 → 带债 | seq1 ✗4 / seq2 ✗2 | 进程被回收（19 次 / 556k） |
| cb-8 | ✗2 次 → 带债 | seq1 ✗4 | 进程被回收（15 次 / 454k） |

**结论 1**：4 轮里有 1 轮产出了可运行的完整系统。
**结论 2**：CONTRACTING 是主要分叉点 —— 2/4 因"任务声明的契约切片没覆盖全部端点"卡住。
**结论 3**：卡住的原因不是"检查太严"，而是 **PM 产出的契约本身有缺陷**：

- cb-7：契约 `paths` 里只有 **1 个**端点（`/health`），却写了 20 个模型、
  而任务图声明了 15 个端点 → 15 条 `phantom-contract-path`（**正确报警**）。
- cb-8：唯一的孤儿端点是 `/api/{any}`（catch-all）→ 检查**误报**（已修：非 `/` 开头的键不算端点）。

**结论 4（代价）**：卡在 CONTRACTING 的两轮会**带债进入 BUILDING** ——
3 条需求在写第一行代码前就被标成 `accepted_with_debt`。这比"慢"严重得多。

## 四、上下文修复前后的对照（根因验证）

| 指标 | 修复前（cb-2） | 修复后（cb-5/6/7/8） |

## 五、锚点自身的准确性（靶场）

```
样本 45：注入 30 + 干净 15
TP 30  FN 0  FP 0  TN 15  严重度不符 0
全部样本符合期望：无误报、无漏报。
```

复核命令：`node scripts/anchor-benchmark.ts`

**为什么强调"干净通过率"**：一条会对好代码报警的检查，会让角色学会糊弄它，
此后所有真报都会被降权。新增的两条可达性检查在自研代码库
（93 文件 / 190 个导出）上**零误报**，这是刻意验的。

## 八、控制台（GUI）—— 不用命令行也能跑

项目**有可视化界面**：`apps/web`（React + Vite）+ `packages/server`（只读 API + SSE 事件流）。

### 启动

```powershell
cd apps/web && npm install && npm run build    # 只需一次；引擎本身仍然零依赖
cd ../.. && node packages/server/src/cli.ts     # → http://127.0.0.1:7788
```

`apps/web/dist` 不存在时服务端会返回「请先构建」的提示页 —— 不会假装有界面。

### 界面上能做什么

| 区域 | 内容 |
|---|---|
| 顶栏 | 模式切换（**离线演示** / **真实 LLM**）、场景下拉、**brief 输入框**、启动按钮 |
| 流水线 | 8 个阶段的状态：通过 / 阻断 N 次 / 未开始 |
| 锚点红绿灯 | 11 条锚点逐条 PASS/WARN/FAIL/SKIPPED，可直接看到最慢看法的证据 |
| 概览 | 当前阶段、锚点发现数、派工单数、主理人 precision |
| 机器抓出来的问题 | 每条都带**归因角色 + 具体消息**（例：`A7 pm 任务声明了契约里不存在的端点 /api/tasks`） |
| 阶段详情 | 每轮门禁的锚点集合与下一步动作（ADVANCE / RETRY_ROLE / ROUNDTABLE …） |
| 真人介入 | 解除阻断·强制推进 / 暂停流水线 / 推翻某个决定 / 明知有问题·继续推进 / 追加硬约束 / 修改需求 |
| 模型与告警 | 能力探测结果（strict / json-mode / prompt-only）与运行时告警 |
| 工件 / 审查 / 事件流 | 全部工件、异议裁决、SSE 实时事件 |
