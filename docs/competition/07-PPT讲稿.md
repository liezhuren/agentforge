## 第 1 页 · 项目概述（40 秒）

**AgentForge —— 让 AI 面对复杂任务时不跑偏、不走样、可被验证**

左：**解决什么问题**
- 上下文越长，目标偏移越严重（而复杂任务必然长上下文）
- 单次生成质量不稳（同一需求两次结果不同）
- 生成结果难以验证（「看起来做完了」≠「真的做完了」）

右：**最终做出了什么**
- 一个多角色研发引擎：8 阶段 · 11 条确定性锚点 · LLM 只产出、不裁决
- 产物 A：可运行的系统（茶歇系统 22/22 测试、33/33 端到端）
- 产物 B：可复核的交付结论（14/14 与 22/22 需求达成，fullyVerified = true）

底部证据条：真实大模型完整交付 ×2 · 每次 7 个门禁 · 两次打回都被修好 · 0 技术债

> 讲稿："先说这是什么、解决了什么。
> 大模型不是不会写代码，问题是三个：任务一复杂、上下文一长，目标就偏；
> 同样的需求跑两次结果不一样；最难的是——**你没法判断它到底做完没有**。
> AgentForge 就是把这三个问题当成工程问题来解决的：切小任务、多角色协作、
> 用确定性检查来验收。今天它已经用真实大模型完整交付过两次。"

## 第 2 页 · 问题与目标（60 秒）

**AI 生成的两个本质问题：随机，且难验证**
副标题：真正的瓶颈不是「能不能生成」，而是「敢不敢把它交付出去」

左：**为什么值得解决**
- 随机性：同一需求两次生成不同 → 无法复现、无法回归、无法承诺
- 难验证：模型说「完成了」，但编译、测试、真实运行都可能不成立；
  而**用另一个 LLM 去验证，等于让被告当法官**
- 实测反例：我们自己的产物 4,443 行、tsc 通过、39 条测试 —— 12 个端点却一律返回 501，
  而当时的检查报「17 个端点全部已实现」

右：**成功标准（可判定，不靠主观）**
1. 机械层全过：编译 / 测试真跑且全绿 / 服务真启动并响应 HTTP 探针
2. 需求层逐条判定：证据必须指向真实文件与真实行号区间；编造 → 整条作废
3. 不许自我满足：空交付 / SKIPPED / 带债 都必须显式记账，且都不算「通过」
   → 三条同时满足 = `fullyVerified`（真·完整交付）

底部：这条标准不是口号 —— 同一套判据刚用出两个相反结果：
① 认证了两次真交付（14/14、22/22）　② 拦下了一次空交付（只有规格、零代码，判 fail）

> 讲稿："为什么这件事值得做？因为 AI 生成有两个本质毛病：**随机**和**难验证**。
> 随机意味着不能复现；难验证意味着不能交付。
> 而如果你再拿一个模型去当裁判，那只是把问题往后挪一层 —— 让被告当法官。
> 所以我们把「成功」定义成三条可判定的东西：机械层全过、需求逐条有真实证据、
> 而且不允许任何形式的自我满足。三条同时满足才有那个徽章。
> 这个标准不是写在纸上的：同一套判据，刚才认证了两次交付，也拦下过一次空交付。"

**视觉**：`docs/competition/evidence/cb-6-ui-home.png` —— 真实界面截图（headless 浏览器，1440×900）。

右侧四块：

## 第 4 页 · 挖根因：不是模型不行，是系统在让人"盲写"（75 秒）

**视觉**：一张"输入 token 随项目规模变化"的折线图 —— 一条**完全水平的线**。

```
输入 token
 12k ┤ ● ● ● ● ● ● ● ●          ← 8 次调用，波动 ±42
     │                    /
  0  └──────────────────────────
      0 行              4,443 行   ← 项目规模
```

**三个数字**：

- 24,000 字符的上下文，被"需求 + PRD + 任务图"吃掉 **95%**
- 54 万字符的工件，真正送达模型的只有 **4.2%**
- 输出/输入 = **2.2 : 1**，**72% 的输出 token 花在重写已有工件上**

**核心一句**：它不是在偷懒，它是在**看不见契约、看不见别人的代码、
看不见"哪条测试挂了"** 的情况下，被要求"把活干完"。
**一个只验收产出、从不验收输入的系统，必然把"饿着写"误诊成"写得差"。**

## 第 5 页 · 架构：编排内核零 LLM（60 秒）

**视觉**：分层图（材料 02 的 mermaid 图简化版）。

```
入口 CLI / Web
   ↓
编排层（零 LLM）  状态机 · Gate · 账本 · 机械裁判 · 圆桌 · 逃生
   ↓
验收层（零 LLM）  A1–A8 事实锚 · B1–B3 语义锚（LLM 提议 + 机械核验）
   ↓
角色层             pm / backend / frontend / test / host
   ↓
能力层            LLM Provider · 三层记忆 · 工件库 · 哈希链日志
```

**三个要点**：
1. **编排里没有一次 LLM 调用** —— 判断逻辑不可能被模型带偏
2. **`SKIPPED ≠ PASS`** —— 环境跑不了时如实报"未验证"，绝不偷偷算通过
3. **8 个阶段共用同一个关口** —— 通过标准不可能在各阶段之间漂移

## 第 6 页 · Agent 链路：不直接对话，只传接口（60 秒）

**视觉**：左侧"错误做法"（全文互传，一张密网），右侧"我们的做法"（星型：所有角色只连契约）。

**两个机制**：

1. **读权限矩阵在代码里强制** —— 不是"请求它别看"，是它根本拿不到
2. **代码层只传接口卡**：11 个模块的全部导出签名 = **5 千字符**，
   而它们的全文 = **20 万字符** —— **差 40 倍**

**核心一句**：切分小任务的意义不是"分给多个模型"，而是**让每个模型只面对它真正需要的信息**。
把全部源码堆进一个大上下文，等于把多角色系统退化成单一大上下文 —— 切分就白做了。

## 第 7 页 · 异常处理：四层逃生，保证不死锁（50 秒）

**视觉**：阶梯图。

```
① 打回返工（便宜、确定）        ← 能归因就先打回，一条都归不了因才开会
② 圆桌会议（唯一允许 LLM 协商）  ← 只"归因完全失灵"才触发
③ 升级真人（一次决定）
④ 带债通过（显式记账）          ← 一定有出口
```

**三个防空转机制**：
- 主理人**阻断 3 次后权限自动终止**（否则两个 Agent 能互相否决到世界末日）
- 已开过圆桌 + 硬失败签名未变 → **不再开会**（实测过某阶段连开 6 次）
- 修复无效 → **直接转逃生**，不重复付费

> 真实日志：[CONTRACTING] 工单修复后硬失败签名未变（pm 的修复没有改变任何东西），
> 不再重复重试，转逃生流程 → 带债通过（受影响需求 3 条）

## 第 8 页 · 可观测性：能回答"它到底看到了什么"（50 秒）

**视觉**：一段真实的 run 日志截图（`context` 字段 + run-progress 输出）。

```
上下文：23,177 / 60,000 字符（39%）  注入 3 个·丢弃 0 个
  其中契约摘要 1 个
  未注入：TaskGraph-001(15520·tier-cap)
```

**核心一句**：这一行是这轮改动最重要的产出。
在这一行存在之前，"为什么它老是做不对"**只能靠猜** —— 我们为此花了两小时复算。

**另外两个可复现性抓手**：
- 决策日志**哈希链**（任何一条被改，链就断）
- **锚点靶场**：45 个样本标定检查本身准不准 → **TP 30 / FN 0 / FP 0 / TN 15**

## 第 9 页 · 结论与展望（30 秒 + 演示）

**已经做到的**：
- **一个 AI 写出来、真的能跑的系统**：22 条测试全过、33 条端到端验收全过（`demo/coffeebreak/`）
- 11 条确定性锚点，401 个测试守着"检查本身是对的"；靶场 45 样本零误报
- 一条可复用的方法论：**先让失败可见，再谈减少失败**

**还没做到的（诚实）**：
- 没有一次自主跑到最终交付（成功那轮在最后一道关卡之后进程被环境回收）
- 四轮并行只成一，**方差还大**
- 语义层（B1/B3）在成功那轮是 `SKIPPED` —— 我们不算它通过

**过渡到演示**："下面是它跑出来的真实系统，以及它在生成过程中自己报过的两个问题。"
