# 05 · 成本与性能

> 所有数字标注来源：`[实测]` = 本仓库真实 LLM 运行 / 本地基准；`[推算]` = 由实测比值推算。

## 一、一次完整生成的成本（`[实测]`）

| 轮次 | 调用次数 | 输入 token | 输出 token | 合计 | 结果 |
|---|---|---|---|---|---|
| cb-1 | 13 | 约 21 万 | 约 34 万 | **550,811** | 4 模块 / 13 端点未实现 |
| cb-2 | 30 | 351,321 | 778,941 | **1,130,262** | 18 模块 4,443 行 / 26 条测试失败（501 占位） |
| cb-3 | 21 | 237,330 | 476,851 | **714,181** | 8 模块 / CONTRACTING 带债 |

按当前网关定价（输入 \$1 / 百万 token、输出 \$2 / 百万 token）折算 `[推算]`：

| 轮次 | 成本 |
|---|---|
| cb-1 | **约 \$0.90** |
| cb-2 | **约 \$1.91** |
| cb-3 | **约 \$1.19** |

> **换算成人民币约 7–14 元/次。** 这个价格决定了"多跑几次取最好"是可行的工程策略，
> 而不是奢侈品 —— 我们这次并行跑了 4 次做统计，总成本不到 60 元。

## 二、吞吐与时间

| 指标 | 值 | 说明 |
|---|---|---|
| 模型输出速率 | **199.7 / 201.4 tok/s** | cb-2 / cb-3，按"输出 token ÷ 模型耗时"算 |
| 模型耗时占墙钟 | **87%** | cb-2：65.0 分钟 / 74.8 分钟 |
| 单次调用平均 | 输入 11.7k / 输出 26k，耗时 130s | cb-2 |
| 一次完整生成 | **40–75 分钟** | 取决于返工轮数 |

**这个数据解释了一个常见误解**："跑了这么久，token 怎么才这么点？"
—— 因为这台网关的模型跑到 **~200 tok/s**，75 分钟的输出就该是 78 万 token，
实测 778,941，分毫不差。**token 数是对的，问题从来不在计数。**

## 三、真正贵的地方：输出端的"重写税"

cb-2 的输出结构 `[实测]`：

| 类别 | token | 占比 |
|---|---|---|
| 首次产出（9 次调用） | 218,320 | **28%** |
| 返工重写（21 次调用） | 560,621 | **72%** |

其中**同一个测试文件被整份重吐 6 次** = 255,283 token，占全部输出 **33%**。

**为什么必须整份重写**：模型看不到自己上一版（上一版被预算挤掉了），
所以它没法"改"，只能"重写"。输出/输入 = **2.2 : 1** 正是这个的签名 ——
一个正常的"填工单"循环，输出应该远小于输入。

> **结论：省钱的关键不在少给输入，而在让模型能"改"而不是"重写"。**

## 四、修复信息饥饿之后的成本模型变化（`[设计]`）

| 项 | 修复前 | 修复后 |
|---|---|---|
| 上下文预算 | 24,000 字符（约 1.1 万 token） | **60,000 字符**（约 2.8 万 token） |
| 契约 | 60,720 字符 → **整件丢弃** | **保证送达**（放不下则确定性摘要，约 4%–6%） |
| 代码 | 全文，**一件都进不去** | **模块接口卡**（5 千字符 vs 全文 20 万，**40 倍**） |
| 测试报告 | **一件都进不去** | **保证送达**（执行事实优先级仅次于契约） |

**预期方向**：输入 token 上升（约 2.5 倍），输出 token 显著下降（因为能改不用重写）。
**净成本大概率下降**，但这一条要等本轮 4 个并行 run 的数据才算数 —— `[待验证]`。

## 五、性能上的三个工程决定

### 1. 零依赖 = 冷启动成本接近零

引擎自身 0 个运行时依赖，Node ≥ 24 原生剥离 TypeScript 类型直接执行。
没有 `npm install` 阶段，克隆下来就能跑测试（398 个用例）。

**代价与收益**：自己写了 dotenv、JSON Schema 校验、strict 模式转换、测试 runner。
但换来"换一台机器也能复现"—— 对我们这种要在评审电脑上现场演示的场景，这个更重要。

### 2. 锚点是纯静态为主，A4/A5 才真正跑命令

| 锚点 | 耗时量级 |
|---|---|
| A1/A2/A3/A7（静态解析） | **3–70 ms** |
| A4（tsc） | 约 40–45 ms（靶场小项目）/ 秒级（真实项目） |
| A5（真跑测试） | 秒级 |
| A6（起服务 + 探针） | **约 330 ms**（含进程启动） |

靶场 45 个样本总耗时约 **2.3 秒** —— 锚点本身不是瓶颈。

### 3. 并行跑：隔离靠端口，不靠祈祷

A6（运行时探针）直接连 `agentforge.healthUrl`。**两个 run 共用 8787 会让 A6 探到别人的服务**
—— 那是比 SKIPPED 更糟的假绿灯。所以并行实验的每个工作区必须声明自己的端口。

（这一条是我们实践踩出来的：第一次并行时工作区忘了预置工具链，
A4/A5/A6 全 SKIPPED，那一轮几乎什么都没验证 —— **预置是运行的一部分，不是可选项**。）

## 六、成本可控性

| 机制 | 作用 |
|---|---|
| `budget.totalTokens` + `onExceed: 'stop'` | 全局 token 上限，超了直接停，不会无限烧 |
| 每阶段阻断上限 3 次 | 防止死循环（实测过某阶段连开 6 次圆桌的烧钱模式） |
| "签名未变则不再重试" | 返工无效时立即转逃生，不再重复付费 |
| 结构化重试只回喂**具体错误** | 比"重试三次取最好"便宜且有效 |

## 七、答辩可能被问到

**Q：一次 1M token，比人写贵还是便宜？**
A：这不是同类比较。人类写 4,443 行 + 39 条测试大约 1–2 人周。
我们的价值不在于"更便宜"，而在于**可复现、可审计、并且会自己说"我没做对"**。
真正的成本对比应该看"返工次数"——这也是我们为什么要把锚点做准。

**Q：为什么不做增量 diff 输出（只改动的部分）？**
A：这是明确的下一步。当前 schema 要求模型输出完整工件（`files[].content` 是全文），
改成 patch 需要新的 schema + 合并逻辑 + 冲突处理。
而**先修信息饥饿是前提**：模型连上一版都看不到，patch 它无从下手。

**Q：60,000 字符的上下文，是不是还是很保守？**
A：是，而且这是刻意的。项目初衷是**把复杂任务切小**、降低单个模型的上下文压力。
我们试过"干脆给 60 万让全部语料进上下文"，被否掉了 ——
那等于把多角色系统退化成单一大上下文，切分就白做了，而且下一个更大的项目会再次溢出。
**正确的方向是"该传的信息本来就该很小"（接口卡），而不是"预算可以一直加"。**
